# Prepared machine

## Reference baseline

The target is a measured `S >= 1.10` over fast Gemma-4-E2B B=1 decoding by overlapping useful computation across the RDMA-connected machines. The existing executor is not a preservation constraint. Source structure and compilation alone do not establish the speedup.

The unchanged `litert-lm==0.17.1` GPU benchmark measured **180.54 decode tokens/s** and **8,963.62 prefill tokens/s** on M5 Max with 1,024 prefill tokens, 256 decode tokens, 2,048 context, speculative decoding disabled, warmup and three measured iterations. The engine's `make e2b-reference` repeats that command. `output_data/e2b-reference-20260918/{benchmark.log,run.json,generation.log,generation.json}` records the benchmark and coherent generation. The package uses WebGPU over Metal. The model revision is `b3ca0d2f076785a8f4b2219ddbd2bdb99954eae1`; SHA-256 is `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c`.

Google's [reference results](https://developers.google.com/edge/litert-lm/overview) and [released model card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm) define the upstream implementation and measurement configuration. This is not a same-weight comparison with the old safetensors executor. The old local 182.378 tokens/s citation was delta-coalesced (`output_data/mesh_e3/run.sh`) and is not a baseline. The 49.146 ms resident numerical rewrite and its constructor have been deleted, including the engine target that built it. Its previous layout and instruction tables are removed with that implementation.

## Prepared operands

`H` is the client's shared-memory mapping address; `A = H + data_off` is its payload address; `P` is the system page size; `q(r,s,o)` is the physical page bound to operand `o` for rank `r` and invocation slot `s` during preparation. These integers are resolved before GPU buffer creation. Each live operand occupies its own canonical pages. Transport registration and the numerical buffer use those same pages.

Vocabulary selection follows the MPI Forum's [MAXLOC](https://www.mpi-forum.org/docs/mpi-5.0/mpi50-report/node135.htm): largest value, with the smallest global token index on a tie. Contiguous increasing row intervals make rank order agree with index order. The pair is represented by two integer words to preserve the index independently of the native backend's floating-storage precision. LiteRT `ARG_MAX`, `GATHER`, `BITCAST`, `PACK`, and integer operations construct and consume that representation inside the prepared numerical graph. The sole transport action is the existing direct push of eight bytes.

M07 uses the MLX authors' [system-coherent Metal accesses and system-scope fences](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/kernels/fence.metal). The payload visibility operation, publication, and consumer observation are recorded at setup alongside the upstream numerical commands. An explicit stop operand supports interrupted measurements. Each rank records only its assigned FFN, publishes its contribution to every prepared consumer, and consumes remote contributions in their final canonical backing. These operations still execute as commands inside the step replay; their crossing latency and across-step residency are not established by this construction.

The [released cache-update parser](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/ml_drift_delegate/delegate/composite/add_values_to_cache_parser.cc) uses three of its seven inputs and writes native byte-format KV outputs in place. Its other inputs support the CPU decomposition and are not read by GPU execution. The original signature still supplies them during setup, using host tensor handles over canonical pages. No floating KV conversion is inserted. Runtime replay uses the native cache output bindings directly. The engine caller aliases corresponding KV input/output names from the upstream signature at setup.

The native Metal binding uses Apple's [no-copy buffer API](https://developer.apple.com/documentation/metal/mtldevice/makebuffer(bytesnocopy:length:options:deallocator:)) and LiteRT 2.2.0's [Metal tensor-buffer import](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/litert/c/litert_tensor_buffer.h). The released `ai-edge-litert==2.2.0` macOS package supplies `libLiteRtMetalAccelerator.dylib` and `libLiteRt.dylib`; the build uses matching release headers. The view covers each operand's page-rounded window, and import receives its logical extent. Mesh owns the pages; `mesh_metal_unbind` destroys the tensor handle and Metal view before the owning pages are released. The WebGPU binding and Dawn SDK generation are deleted. The measured reference executable remains unchanged.

`make e2b-prepare` prepares the original decode graph. `make e2b-partition E2B_PLACEMENT=11,5` partitions its FFN columns using caller-supplied proportions; the example gives intervals `[0,4224), [4224,6144)` or `[0,8448), [8448,12288)`. The manifest names the prefix, 35 FFNs and 35 consumers, including each input and live output. Each consumer includes the original finishing operations and following attention; the last includes the vocabulary projection. `extract` exports every produced value used outside the selected operators, including KV outputs. The manifest covers all 2,068 original operators exactly once, with no missing dependency or final output in either the unsplit or two-rank graph. This is graph preparation, not full-step execution. The partition uses [Shoeybi et al.'s column decomposition](algorithm-sources.md#nnffn); gate/up projections preserve their original quantization, down projections return floating contributions, and addition precedes output quantization as in [Jacob et al.](https://arxiv.org/abs/1712.05877). Existing LiteRT operators perform attention, norms, residual, PLE and vocabulary work; no custom numerical kernel is introduced.

## Executed connection

`output_data/e2b-native-metal-20260918/{prepare-run.json,execute-run.json,execute.log}` records the released native Metal backend preparing and executing the original first FFN on canonical Mesh pages. Both operands require 3,072 bytes; all 1,536 output values are finite, 1,524 nonzero. The client and isolated bridge exit 0. Planned bytes: 67,960,832 arena + 67,108,864 model/upload + 536,870,912 compiler = 671,940,608. The measurement explicitly waits for native queue completion before reading output; production publication and replay are not implemented by the page binding. `graph-full.json` and `graph-11-5.json` record complete source-operator and dependency coverage, not a numerical or throughput result.

`output_data/e2b-rdma-preparation-20260918/operand-layers.json` and `operand-layer-{0,15,34}.log` record execution of reference FFNs on real canonical Mesh pages through LiteRT's WebGPU backend. All three produced 1,536 finite FP16 outputs; the native clients and isolated bridges exited 0. Both 6,144-column INT4 and 12,288-column INT2 FFNs were exercised. The arena was 76,922,880 bytes; model/upload allowance was 64 MiB and compiler allowance 512 MiB. No network device or persistent dispatch was opened. Elapsed process times include setup and are not throughput measurements.

Native queue completion was observed explicitly by the measurement client before it read the shared output. External-buffer execution supplied no LiteRT tensor completion event; returning from `LiteRtRunCompiledModel` did not establish CPU-visible completion. The page-binding library contains no invocation, wait, completion callback or scheduler. Production publication at the numerical boundary and its connection to preposted cross-node transfers remain unimplemented. No crossing latency or `S >= 1.10` result exists yet.

`output_data/e2b-partition-20260918/{runs.json,combine-runs.json,comparison.json,cost.json}` records both rank contributions and their native combination for layers 0, 15 and 34. All graphs reported full non-CPU acceleration and returned finite values. Different floating accumulation order changes rounding at quantization boundaries: 10, 23 and 9 of 1,536 outputs differed from the respective unsplit graph; no bitwise-equivalence claim is made. The source-refactored generator reproduced all 105 exercised-format model artifacts byte-for-byte. These isolated repeated-layer timings are not decode timings: weights remain cache-hot, and a separately invoked combination cost 21.8–33.1 microseconds. The emitted consumer now incorporates that addition into the original finishing graph; no separate combination artifact is referenced by the manifest.

`output_data/e2b-consumer-20260918/{runs.json,comparison.json,three-ranks.json}` records native GPU execution of the composed consumers for layers 0, 15 and 34 and a three-contribution consumer. All 1,536 values in each of the three compared layers equal the original finishing graph fed by the previous separate combination. The two- and three-rank configurations prepare all 35 consumers. These are isolated graph executions, not a distributed decode speedup.

## Native replay

`metal_recording.h` exposes a 32-byte, 32-byte-aligned `MetalReplay`. `MetalRecorder.record` accepts the upstream encoder function and records its pipelines, grids and buffer bindings into an Apple indirect command buffer. The recorder captures only preparation. Replay calls `useResources` and `executeCommandsInBuffer`; it does not call LiteRT or rebuild bindings. Apple's [ICB barrier contract](https://developer.apple.com/documentation/metal/mtlindirectcomputecommand/setbarrier()) supplies the original serial compute-encoder ordering. The released native delegate creates its own device; the recording library uses Apple's [dyld interposition mechanism](https://github.com/apple-oss-distributions/dyld/blob/main/include/mach-o/dyld-interposing.h) to request indirect-command-compatible pipelines at creation. The reference executable is not linked to this library.

The preparation queue uses explicit `requestResidency`/`endResidency` for the upstream model sets, then replay declares the prepared resource list. It does not attach one set per fragment to the queue, which exceeds Apple's [32-set queue limit](https://developer.apple.com/documentation/metal/simplifying-gpu-resource-management-with-residency-sets). All registration and release work is outside replay.

Engine `tools/e2b_replay.m` constructs the whole native chain from `operands.json`, including both upstream embedding graphs, all 35 FFNs, attention and finishing consumers, and vocabulary projection. A partitioned manifest supplies distinct `layer_l/contribution_r` operand names; the same caller can execute all contributions locally. It destroys compiled LiteRT executors before GPU replay. The recorded kernels and their resources remain owned by `MetalReplay`. One native command buffer is submitted per observed decode step; this is not an across-step persistent dispatch or a completed distributed implementation.

The manifest carries the upstream [packed-weight options](https://github.com/google-ai-edge/LiteRT-LM/blob/main/runtime/executor/llm_executor_settings_utils.cc) and [context replacement](https://github.com/google-ai-edge/LiteRT-LM/blob/main/runtime/executor/magic_number_configs_helper.cc). `--context` defaults to the reference's 2,048. The caller supplies `LiteRtMagicNumberConfigs` before model compilation, through writable private model mappings because replacement mutates shape metadata. Read-only `CreateModelFromFile` produced a protection fault in `ReplaceMagicNumberInSubgraph`; the private mapping changes metadata without rewriting model files. The causal boolean mask and runtime parameter operands follow the upstream executor utilities.

`output_data/e2b-metal-replay-20260918/replay-boolean-mask{.log,-run.json,-memory.json}` records the current complete local chain: 1,371 native commands, 3,325 resources, 22,003,712 canonical operand bytes, sixteen token-feedback steps, and clean client/bridge exits. Every step produced 262,144 finite, nonzero logits. Warm GPU execution spans 6.098–6.890 ms. This is a BOS-seeded GPU replay measurement with no prefill or RDMA, not the reference benchmark configuration or evidence of D2. Earlier runs used an incorrectly typed attention mask and are not model-performance evidence. The unchanged 180.54 tokens/s reference remains the denominator; the required distributed speedup is unestablished.

## Paired preparation and native limits

The M5 and Mini built engine `0f78994` and Mesh `ef23833` from committed Git objects. Both prepared 1,476 commands, 3,502 resources and 32,047,104 bytes of canonical operands for their assigned FFN shards. The attempted run stopped before GPU replay: M5 transport setup returned `EIO`; the Mini's connection attempt expired. Both clients returned 1 and both bridges returned 0. Peak observed wired memory was 8,066,318,336 bytes on the M5 and 2,195,554,304 bytes on the Mini, against planned per-node allocations of 9,967,504,336 and 9,589,832,656 bytes. Records are `output_data/e2b-rdma-replay-20260918/rank{0,1}-*.json` and logs in the engine checkout. No distributed timing is inferred.

The M5 provider reports `max_mr_size=16,384,000`, `max_qp=11`, and `PORT_DOWN`; the IP interface remains active and the Mini reports `PORT_ACTIVE`. The attempted source requested a 512 MiB registration and 70 QPs. M09 replaces the unsupported registration assumption with device-sized extents. M08 replaces one-QP-per-transfer with one bidirectional QP per configured independent stream and invocation slot: one QP for this pair's B=1 graph, with 35 receives preposted in the sender's prepared order. The dedicated TX cursor advances on acceptance and cycles across independent streams, never across the graph looking for a ready layer. These changes compile; the pair has not been relaunched while the port-down condition remains unexplained.

ABI 89 deletes the unobserved invocation/completion counters and status construction. Neither numerical execution nor the client reads them; they were extra atomic operations on every TX/RX completion. Page lifetime still follows client ownership and native queue teardown. The emitted native loops have no accepted-event register spills: TX uses an 80-byte frame, RX 64 bytes. The obsolete 37/37 and generated-kernel load table is replaced by the current native instructions in `hot-path-loads.md`.
