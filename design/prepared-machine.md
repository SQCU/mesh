# Prepared machine

A program's prepared objects: each one's address, extent, the code that constructs it, and its use at run time. The
transport's are the bridge's and libmesh's (`rdma/`), and a kernel reaches them through `rdma/mesh.metal` (M07, M10,
M12, M30). The numerical program's are its front end's: metal-microbench `litert_program.m` (the LiteRT program),
through `mesh_rank.h` (a rank's operands, crossings and recording) and `metal_recording.h` (the recording and its
replay). The collectives over them: `rdma/NCCL.md`.

## Reference baseline

The reference is the unchanged `litert-lm==0.17.1` GPU benchmark: 1,024 prefill tokens, 256 decode tokens, 2,048
context, speculative decoding disabled, a warmup and three measured iterations, WebGPU over Metal, model revision
`b3ca0d2f076785a8f4b2219ddbd2bdb99954eae1` (SHA-256 `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c`).
metal-microbench's `make e2b-reference` repeats that command, and its records are output_data's. Google's [reference
results](https://developers.google.com/edge/litert-lm/overview) and [released model
card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm) define the upstream implementation and its
measurement configuration.

## Prepared operands

`H` is the client's shared-memory mapping address; `A = H + data_off` is its payload address; `P` is the system page size; `q(r,s,o)` is the physical page bound to operand `o` for rank `r` and invocation slot `s` during preparation. These integers are resolved before GPU buffer creation. Each live operand occupies its own canonical pages. Transport registration and the numerical buffer use those same pages. The bridge lays out physical payload pages and logical mapping rows independently, from the node's memory (`mesh_layout`, design/bridge-and-ipc.md#region): rows hold mappings, ownership and transfer descriptors, at least one a physical page, while the payload extent remains the arena. `mesh_arena_pages` derives physical pages from `(length-data_off)/(block*P)`; physical allocation and registration never use the logical row count. `mesh_section_slice` keeps its mapping into canonical pages, including disjoint invocation ranges. Alias capacity is setup metadata, not payload copies, registered regions, runtime lookup or a hot-path operation. This separates logical indexing from physical backing as in `algorithm-sources.md#programtensor`.

The [released cache-update parser](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/ml_drift_delegate/delegate/composite/add_values_to_cache_parser.cc) uses three of its seven inputs and writes native byte-format KV outputs in place. Its other inputs support the CPU decomposition and are not read by GPU execution. The original signature still supplies them during setup, using host tensor handles over canonical pages. No floating KV conversion is inserted. Runtime replay uses the native cache output bindings directly. The engine caller aliases corresponding KV input/output names from the upstream signature at setup.

The external WebGPU binding imports the actual M01 pages through Dawn's host-mapped buffer extension. Each canonical operand has one WebGPU buffer, shared by all LiteRT views. Native numerical commands use that object's Metal buffer through the pinned provider's [Buffer::GetMTLBuffer](https://dawn.googlesource.com/dawn/+/refs/heads/main/src/dawn/native/metal/BufferMTL.mm) accessor. That accessor is setup-only and is not a stable public Dawn ABI. The reference library supplies the numerical kernels.

`litert_program.m` makes the WebGPU device with the adapter's host-mapped pointers, f16, subgroups, subgroup matrices and implicit synchronization where the adapter has them, its native limits, and the toggles `allow_unsafe_apis`, `disable_robustness`, `disable_polyfills_on_integer_div_and_mod`, `disable_workgroup_init` and `disable_symbol_renaming`, before compilation. The reference provider is the same `liblitert-lm.dylib` used by the benchmark. [Dawn host-mapped buffers](https://dawn.googlesource.com/dawn/+/HEAD/docs/dawn/features/host_mapped_pointer.md) use the canonical pages; the native Metal view for transport names those same pages. Device and queue interception applies only during preparation. Dawn's first-use buffer initialization and native queue completion signals finish before recording returns. They are not replayed at decode boundaries. The prepared resource set owns the numerical bindings after the LiteRT executors are destroyed.

The manifest carries the upstream [packed-weight options](https://github.com/google-ai-edge/LiteRT-LM/blob/main/runtime/executor/llm_executor_settings_utils.cc) and [context replacement](https://github.com/google-ai-edge/LiteRT-LM/blob/main/runtime/executor/magic_number_configs_helper.cc). ## Cyclic programs and programs within an attach

<a id="M30"></a>**M30, cyclic invocation.** A client may declare its prepared program cyclic
(`mesh_transfers_cyclic`, after `mesh_transfers_prepare`, before `mesh_transfers_start`; the header's
`cyclic` word, zero for every one-pass program). Running invocation T is prepared invocation T mod N in
cycle T / N, N the program's invocations; every transfer's ring depth divides N and every range covers
the program. The producer releases T by storing the cell's argument plus the cycle into cell T mod N
(`mesh_host_publish`, or `rdma/mesh.metal` `mesh_publish` from a kernel); the send stream follows its last cell with its
first and counts cycles, posting a cell whose ready word exceeds its cycle, and relinks each request after
posting it. The receive ring's posted count runs on: record `posted mod count` in cycle `posted / count`,
its span held under N so a record is posted again only after its previous posting completed (receive
completions arrive in order); a landing stores 1 plus its cycle into the completion word. A reader of T
waits for a word of at least 1 + T / N (`rdma/mesh.metal` `mesh_remote_wait`); `UINT64_MAX` (M12) still ends every wait. For a one-pass program
the cycle is always 0 and every comparison is the one before M30. NCCL's FIFOs [NCCL `src/transport/net.cc`]
and persistent communication buffers [PyTorch `torch/_inductor/comm_lowering.py`: "the same allocation, at the
same offset, in every iteration"] are the users this serves.

A client's program ends with its attach: `mesh_detach`, or the client's process exiting, retires its slot, and the
bridge ends the program on every port (design/bridge-and-ipc.md#clients). A client that runs another program attaches
again.
