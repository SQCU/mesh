# Prepared machine

A program's numerical prepared objects: each one's address, extent, the code that constructs it, and its use at run
time. They are the program's front end's: metal-microbench `litert_program.m` (the LiteRT program), through
`mesh_rank.h` and `metal_recording.h` (the recording and its replay). The transport's objects are design/transport.md's.

## Reference baseline

The reference is the unchanged `litert-lm==0.17.1` GPU benchmark: 1,024 prefill tokens, 256 decode tokens, 2,048
context, speculative decoding disabled, a warmup and three measured iterations, WebGPU over Metal, model revision
`b3ca0d2f076785a8f4b2219ddbd2bdb99954eae1` (SHA-256 `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c`).
metal-microbench's `make e2b-reference` repeats that command, and its records are output_data's. Google's [reference
results](https://developers.google.com/edge/litert-lm/overview) and [released model
card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm) define the upstream implementation and its
measurement configuration.


## Prepared operands

| Object | Prepared address | Extent | Constructor | Runtime use |
| --- | --- | --- | --- | --- |
| Native GPU and LiteRT operand handles | Prepared operand and binding addresses | One WebGPU buffer per canonical operand (`MeshOperand.owner`), one LiteRT handle per typed view; no transport event record | metal-microbench `litert_program.m` imports each operand's pages once through Dawn's host-mapped buffers, then creates LiteRT views of that buffer | No per-event access: recorded M06 bindings name the one canonical GPU resource. No payload copy, map/unmap, allocation or mesh callback is added by this binding during numerical execution. |
| Reference decode graph and weights | Prepared upstream model and native objects | The original decode operators; each member's FFN columns and attention heads, as the program record gives them, with original packed INT4/INT2 weights; the selection, the draw at temperature 1 (metal-microbench docs/kernels.md#speculative-decoding, sampling), writes the 4-byte token operand | metal-microbench `tools/prepare_e2b.py:prepare` (the program record of `tools/mesh/programs.py derive`), `partition`, `vocabulary`, upstream `LiteRtCreateCompiledModel` | Existing LiteRT kernels execute the arithmetic. At preparation, `tools/prepare_e2b.py:lower_rotations` replaces the original split-half rotation expression with ML Drift’s [existing RoPE operand interface](https://github.com/google-ai-edge/LiteRT/blob/main/ml_drift_delegate/delegate/composite/rope_parser.cc); the original expression supplies its decomposition. Geometric frequency constants and the position operand determine attributes at setup; a geometric prefix followed by zero frequencies uses the same native operation’s `proportion`, with the prefix ending on its four-channel vector boundary. Prefill and decode use the same lowering. No mesh arithmetic, callback or runtime matcher is introduced. |
| Rank contribution and consumer operands | `A + P*q(r,s,o)` for each rank contribution | FFN: the layer's output width in FP16 per row. Vocabulary: the draw's pair (M16) | `tools/prepare_e2b.py:partition`, `vocabulary`, `append`, `save`: one graph per rank, local partials its outputs and remote partials its inputs, crossing at the record's points under its crossings' operands | A member with no columns of a layer has no contribution for it; with one contributor the sum is the identity and the owner keeps the original unsplit FFN and its quantization. Contributions are summed in the record's publication order, with the original quantization and finishing operations after the complete sum, so the output quantization stays after the sum and the input DEQUANTIZE stays (the released provider's `fully_connected.cc` requires an integer output for an INT8 input). `save` removes only operations unreachable from the retained outputs ([MLIR dead-value elimination](https://mlir.llvm.org/docs/Passes/#-remove-dead-values)); original KV outputs remain roots. Shape selection, graph slicing and bindings run only at preparation; the library transports every operand alike and does not interpret its arithmetic. |
| <a id="M06"></a>Recorded native compute program | The replay's indirect command buffers, invocation `t`'s commands at its prepared range | `struct MetalReplay` (commands, residency set, owner, count), 32 bytes, `_Static_assert` in metal-microbench `metal_recording.h` | `metal_recording.h` `MetalRecord`: a recording device (`MetalRecordingDevice`) captures the compute dispatches the front end's block issues (each pipeline with its reflection, its bound buffers and offsets, its grid) as one invocation, binds each `MetalOperand` by slot, and sets a barrier where a command's dependency level rises, the levels from each pipeline's reflected reads and writes (a command whose reflection cannot show its dataflow is a full barrier); it prepares the invocations in its form (`MetalFormIndirect`, its command buffers optimized with Apple's [range optimizer](https://developer.apple.com/documentation/metal/mtlblitcommandencoder/optimizeindirectcommandbuffer(_:range:)); or `MetalFormEncoded`). `mesh_rank.h` `MeshRankRecord` records a front end's program as a rank's: the recording holds the program's kernels alone, and each crossing (`MeshRankCross`, a libnccl-mesh call) ends a segment, the rank issuing it between segments | `MetalReplaySubmit` runs invocations `[first, first+count)` as one Metal 4 command buffer; Metal 4 [requires residency for indirectly referenced pipeline states](https://developer.apple.com/documentation/metal/mtl4computecommandencoder/executecommands(buffer:indirectbuffer:)). No recording, LiteRT invocation, host command construction or operand staging happens between invocations. No pass splices one kernel's text into another's. |
| <a id="M13"></a>Prepared invocation operands | Parameters, position, mask and token: each a host operand of slots of its native extent rounded up to 16 bytes, invocation `t` binding slot `t mod slots`; the token's output one slot past its input (`MetalOperand` `outputOffset`) | 32-byte `DecodeParameters` and 4-byte INT32 token and position, `_Static_assert` in metal-microbench `litert_program.m`; the mask its declared context extent | `litert_program.m` writes each step's position, mask and cache parameters (`{start, end, end}`, LiteRT-LM's `FillSingleBufferCacheParamTensor`) into its slot, and the prompt's last token into the token's first, before the transfers start; `MeshRankRecord` binds each slot in the recorded commands | Numerical functions read or write directly bound operands; 0 loads to reach them. The draw writes the next token's slot and the next embedding reads that same slot. No state record, boundary dispatch, metadata copy, token copy, runtime binding lookup or offset calculation. |
| <a id="M14"></a>Reference prefill operands | `A + P*q(r,prefill,o)`, a slot a chunk: token ids, positions, cache parameters and the call's record; KV outputs bind the same operand pages decode uses | The prefill signature's extents at batch 1 | `tools/prepare_e2b.py:prepare` extracts the original prefill signature; `litert_program.m` writes each chunk's token ids (its last page zero-padded), positions from its start and cache parameters `[start, start+length, start+length, 0, 0, 0, 0]`, and records the prefill as the rank's program run before the transfers start | The prefill populates KV directly, following Google's [prefill input construction](https://github.com/google-ai-edge/LiteRT-LM/blob/main/runtime/executor/llm_litert_compiled_model_executor.cc): the last prompt token remains pending for decode. LiteRT's [input resize API](https://github.com/google-ai-edge/LiteRT/blob/v2.2.0/litert/c/litert_compiled_model.h) realizes the embedding functions for the prefill scope before buffer requirements are queried. No additional command buffer, host wait, output copy or runtime rebinding is introduced. |
| <a id="M15"></a>Prepared index-expression operands | `A+P*q(r,index)+i*S_index`; `S_index` is the native extent rounded up to 16 bytes, realized for each invocation at setup; static-input experiments bind the same immutable slice | Native provider extent for each original output; INT32 is pinned by the M13 4-byte `_Static_assert`; no event record | metal-microbench `tools/prepare_e2b.py:save` separates the pure graph rooted in supplied position, parameter and mask operands plus constants; the original operations become a preparation program and their frontier outputs become numerical inputs. `litert_program.m` allocates those outputs in canonical operand pages, records and runs the index program before the transfers start, and binds each output slice directly in M06. Token, activation, KV and remote operands are not preparation roots. Source tensor identity in `extract`/`append` deduplicates shared expressions before separation | Numerical functions read the prepared original results, 0 loads to reach their native operand binding. The original index operations execute only during preparation, following [OpenXLA constant folding](https://openxla.org/xla/hlo_passes#constant-folding); no expression graph, lookup, callback, copy or integer dispatch remains between numerical stages. The finite invocation range and all position-dependent results exist before submission. |
| <a id="M16"></a>Vocabulary pair | Every holder's pairs end to end in `vocabulary` (operand pages), the holder's at its place among the holders, a row's after another | 8 bytes a row: the value's bits and the token, the packed crossing `rdma/torch-mesh/torch_mesh/argmax.metal` `mesh_take` merges | metal-microbench `tools/prepare_e2b.py:vocabulary` shards the projection by the record's vocabulary rows and emits each holder's `draw` and each member's `take`, both prepending `argmax.metal`; `litert_program.m` binds them | Producer: the holder's draw over its columns (`mesh_draw`), one pair a row. Consumer: the take, `mesh_take` over each holder's pair (the greater value, then the lower token), writing the token operand (M13). The transport carries the pair as an ordinary operand; no candidate array is kept. |
