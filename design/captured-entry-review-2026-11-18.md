## B: What the caller supplies and what the compiler must emit

At Mesh `75d141ef`, the three example modules that imported the driver called `compile_module`. The target supplies its signature when the driver returns the schedule. The crossing example calls `self.work(x, y)` in a loop. Its `functions={'work'}` argument identifies that submodule to the Torch exporter. PyTorch’s optional `preserve_module_call_signature` records how the submodule takes its arguments and returns its results, so `unflatten` can reconstruct that interface. A10 concerns the graph itself. Each call identifies its callee and operands. The compiler uses those calls to determine dependencies and how many invocations may overlap. A compiler that receives that graph can use those references directly. Whole-program Metal emission has a concrete missing operand. The planner holds the function table and the function index for every call. The target constructor selects one function. Fresh recorder installation repeats its handle across every call row. For the example above the recorder needs the handle for `a` in rows zero and two and the handle for `b` in row one, with each row’s operand bindings from the selected plan.
