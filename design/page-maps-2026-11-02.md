# Page maps: choosers know pages, effectors know pointers (2026-11-02)

This note records a rule, the defect that exposed it, and the joint change it requires. The inventories that list
every violation are in design/data/ (permissions-compiler, permissions-frontend, send-receive-wrappings, all
2026-11-02). Where they are not yet written, this note names what they must cover.

## The rule

The operator, 2026-11-02:

- "choosers don't know about pointers, only about pages; effectors know about pointers and pages but never make any
  decisions ever. this system of constraint is both performant and memory safe *for the same shared single reason*."
- "the compiler doesn't work in pointers, offsets, etc ever, because it shouldn't have access to certain abstractions
  at all."
- "for some kernels the right thing to be reading is literal pointers, but pointers that only appeared in the data
  flow through the dereferencing of page table indices to pointer literals. … the final runtime code must be as fast
  as possible, as if it was 'hand written', but our code which generates templates or data dependencies or whatever
  may not have specific apis or specific types in order to make data-related or type-related inferences or choices."
- "get rid of every single case where a scope is trying to use an abstraction they don't have 'permission' to use,
  correct them all at once so nobody tries to grow them back, and address all of the issues all of that code was
  trying to handle (also all at once) so that nobody tries to 'invent' them again."

What the terms mean here:

- A chooser decides. Placement, storage, layout, order, routing, schedules, waits, thresholds and hazards are its
  work. The compiler, the planner, page effects and the solver are choosers.
- An effector carries out a decision. It evaluates a decided page map into addresses: a kernel's loads, a bridge SGE,
  a CPU store. It holds pointers. It decides nothing.
- The one shared reason: a chooser that sees only page maps can answer every question by algebra on maps. A pointer
  makes aliasing, lifetime and hazard opaque. Then each question grows its own special case and its own run-time
  guard. An effector that decides is where waits and checks get invented.

## The defect that exposed it

The five-rank LSTM idled 77–101 ms a tick on all ranks at once (metal-microbench docs/facts.md, 2026-11-02). The
chain of causes:

- The program lands every tick's gather in place: `allgatherv_out(mine, h)` into one `h`, and the service replays a
  one-tick declaration over it. So h(t+1) lands in the same bytes as h(t).
- Placement binds that value to the same pages at every invocation. The binding interface offers only
  `ncclMeshBufferSlots`: "slot × stride bytes past buffer.offset". That is pointer arithmetic.
- The library guards the reuse by position. A group's tables reach the bridge only when the GPU runs its link
  (nccl-mesh.c `zinth`), and the native bind records the link at the occurrence's own position. So each tick's
  receives are posted after the products that read h(t).
- The peers' SENDs race those late receives. A SEND that wins waits in the hardware's credit (TN3205).

Two halves carry one misapprehension. The program assumed the library makes in-place landing safe. The library
assumed programs reuse pages, so it guards by position and spends the credit. The specification already rules both
out:

- design/eager-execution.md: "Page reuse is answered by page assignment over the declared function (Freeing 7).
  Receipts, credits, waits on `sent` … are never the answer."
- design/whole-function.md: "Distinct landing generations or an existing causal descendant proof are required; the
  recurrent gather's two-slot theorem cannot be assumed."

## The data flow, and where pointers enter choosers

1. The program defines values each tick: z, c(t+1), h(t+1). An `out=` argument and `copy_` name a new version, not an
   address.
2. Capture and functionalization keep them as values. h(t+1) is a fresh node; the state write is a final writeback.
3. Placement turns values into addresses. This is the first chooser that holds offsets: fixed bindings, `(buffer,
   offset)` pairs, `slot × stride`, cyclic `instances`.
4. Page tables and kernels. `ncclMeshPageTableCreate` and `Compose` build tables of region pages. Generated kernels
   address through `mesh_storage_N(i)` and `mesh_index<k>`, which evaluate a map at run time, divisions included.
5. The transport plan turns entries into exact region spans. `zinth` hands them to the bridge.
6. The bridge posts receives and SENDs once linked, and advances `sent` and `landed`.
7. The consumer waits on `landed`. This is the one true data edge (read after write).

The hazard is made at step 3. It is then patched at steps 5 and 6. Renaming belongs at step 3.

## The target model

- One explicit, functional representation of address maps. For each value: invocation → (virtual page → physical
  page), composed with its layout (logical index → virtual byte). Views of views are compositions.
- Operations on maps answer every chooser question:
  - aliasing and hazards: do two maps' images meet over overlapping lifetimes?
  - renaming: a value definition gets fresh virtual pages;
  - freeing: a physical page's lifetime is the union of the virtual uses the map sends there. It returns to the free
    set when the ledger's completion prefixes prove its last access retired (rdma/mesh-lease-retire.h): local reads,
    SEND reads and landings;
  - DMA spans: the image of a landing's map, the same image at both ends;
  - waits: a consumer tile's threshold is the preimage of the tile through layout, page map and DMA unit order. This
    is the mask-mod closure the operator asked for streaming partial consumption.
- Allocation bin-packs values over the region's physical pages by exact lifetimes. Adjacent invocations of a repeated
  function never overlap where both are live. Every write is then one-sided: no check, no wait, no sync. Every receive
  of an invocation can be posted at its start.
- Specialization. Every realized run's schedule exists before it runs. So the final lowering evaluates the map
  family at each invocation. It writes pointer literals, or a base and an affine offset, into the recorded commands.
  Run time reads constants. No kernel evaluates a map; no effector chooses.

## Why no rings

A ring (cyclic slots, i mod N) is one hand-picked map. It is prohibited for these reasons:

- It makes the race on purpose. The reuse distance is fixed in the address, not in the lifetime. Whether iteration
  i + N may write slot i mod N is a run-time fact. So every ring needs a run-time guard, or a causal proof that holds
  for every schedule. The in-place `h` is the ring with N = 1, and its guard was the hardware's credit.
- It is a bounded buffer with blocking writes, and collectives are cycles. Such networks can deadlock with every
  member healthy (Kahn 1974; Parks 1995, cited in design/eager-execution.md). Bounded-memory scheduling of dynamic
  dataflow is undecidable (Buck 1993).
- This codebase has paid for rings already. The stream's 4,096-entry rings deadlocked the chain service (test-ov3,
  2026-10-31; deleted, design/zorvek.md). The relay rings needed credited slots, and the 7-line's middle link stopped
  with both ends holding data (metal-microbench docs/measurement.md).
- It is pointer arithmetic, so the compiler cannot remap a slot. Consumers compute modular addresses: the floor and
  mod "addressing artifact", at run time and in isl.
- It retires in order (FIFO). Independent work queues behind the oldest slot. A free set retires out of order.
- No hardware limit calls for one. The region is the whole memory less about 10 GiB, and every engine reaches it
  through the page table.

## Why one representation, not one fix per case

Each addressing scheme in the code is one map, encoded separately in its own layer:

- in-place landings, fixed bindings, `slot × stride`, cyclic `instances`, chain.py's generations;
- row-major and units-first layouts, `TensorLayout`, `MetalTensorLayout`;
- the written inverse and preimage (`MeshIndexInverse`, `MeshIndexPreimage`), `IndexRelation.through`;
- page tables and their composition, stream-page tables;
- landing and SEND spans as raw region offsets;
- `mesh_storage_N`, `mesh_index<k>` in kernels.

Lifetimes are not uniform, so no fixed formula fits:

- the wavefront's layer-l h is read one tick later by layer l + 1;
- a forwarded piece lives until its relay SEND completes;
- descriptor tables live until the bridge's CPU leaves them;
- ranks finish at different times;
- granularities differ: 16 KiB pages, 4 KiB frames, tiles, rows.

The defects of 2026-10-31 to 11-02 were each this one defect, patched as a special case:

- floor and mod relations that made isl eliminate divisions (a map stored as a relation, not as a function in
  coordinates);
- the written inverses and preimages added one at a time;
- the layout-union stall;
- the per-element gather lowering;
- the descriptor-for-contents SIGSEGV and the reach slot −1;
- the late receives;
- the ring deadlocks.

## The page-table interface today runs the wrong way

rdma/nccl.h's page tables exist, but they are derived from pointers:

- `ncclMeshPageTableCreate(const void* local, …)` makes a table from an address.
- `ncclMeshRegionRuns(const void* local, bytes, …)` reads a range's physical runs back from an address.

So a chooser starts from a pointer and recovers pages. The rule needs the other direction, and its parts exist:

- `ncclMeshPageBacking {first, count, page}` names physical page identities. That is a chooser's object.
- `ncclMeshPageTableCompose` composes selections of pages and copies nothing. That is a map operation.
- `ncclMeshPageTableAddress` and `ncclMeshPageTableBinding` produce an address or a Metal binding. Only the final
  lowering may call them.

In the joint change a chooser allocates page identities from the region's free set, composes them per invocation,
and hands the result to the final lowering. Create-from-pointer and RegionRuns leave chooser scope.

## The joint change

Both sides of each interface change together. No side is changed, tested and then followed by the other: each half
alone is a no-op or is wrong. Program-side generations with the link still at its position leave the race. A link
placed earlier over one reused `h` either moves nowhere or lets a fast peer overwrite h(t) under a slow rank's
products.

- Choosers: placement, page effects, the planner and the native bind lose every pointer-yielding API and concrete
  byte type. They hold page maps only. The inventories list each site and the problem it handled. Each problem gets
  one map operation as its answer.
- Effectors: kernels, the bridge and the recorder evaluate specialized maps only. Every condition, bound or choice
  in them goes, or moves to a chooser as a compile-time fact.
- The link: recorded at each invocation's start. `MetalPageArrivalReaders` (written 2026-11-02, held with this
  change) stays as a detector. Under renaming no earlier command touches an arrival, so a line in its record marks a
  page-assignment defect. It never selects a later order.
- The SEND lists stop waiting on the link. `ready` and the hardware's credit already gate them.
- Interfaces in rdma/nccl.h that become incompatible: `ncclMeshBufferSlots` (`stride`, `instances`, `invocation`) and
  `ncclMeshInvocationIndex`; `ncclMeshBuffer {buffer, offset}` wherever a chooser receives it; the stream and
  binding structs that carry region offsets into choosers.
- Programs: lstm.py keeps one `h` value a tick and no hand-made generations. chain.py's two generations go. Renaming
  is the compiler's.

## Guard, sync and wait

The partial-tensor contract (design/deliverables.md) already forbids waits around transfers:

- I2: "A producer publishes when its writes are visible, and returns."
- I3: "Presence is the receive completion. The data path carries no acknowledgement, handshake, health check, credit
  protocol or in-band sentinel."
- I4 (2026-09-15): "dependent loads axiomatically cannot sync or guard or induce waits for transfers." Its clause
  allowing "page reuse on a fixed ring" is superseded by the operator's 2026-11-02 "no ring buffers ever".
- I18: "No barrier, acknowledgement, reuse guard, blocking retry or wait for a particular value holds up independent
  publication, transfer or consumption."
- L3: "Publication on visibility, firing on presence … No consumer evaluates 'are my inputs present'."
- The operator, 2026-09-14 (collective-goals-2026-09-14.md): "all queues must be drained IMMEDIATELY WITHOUT EXCEPTION
  WITH NO WAITS SEPARATING QUEUES FROM BEING FILLED AND EMPTIED."
- The operator, 2026-10-22 (hardware-and-discipline.md): "data processing code gets to write their own guards in their
  own source … the nic must write continuously into that buffer even if this means that data processing code can race
  or lose parts of a stream."

The three terms, in a streaming multiprocessor's vocabulary:

- A guard is a predicate on data: a bounds test, a load mask (Triton's `tl.load(…, mask=)`), FlexAttention's
  `mask_mod`. It never blocks. It decides what to compute with what is present.
- A sync orders participants of one scheduling domain: `__syncthreads`, an `mbarrier` among a block's threads, Metal's
  `threadgroup_barrier`. All participants are resident and making progress, so it ends in a time set by local work. A
  blocked warp is parked, not spinning. Asynchronous data joins this domain only when the domain itself issued the
  copy: Hopper's TMA arrives on an `mbarrier` with its byte count.
- A wait blocks on an agent outside the domain whose progress it cannot see: a word the NIC, the bridge or a peer
  writes. It spins, holding issue slots and making a system-scope fence each poll. If that agent depends on the
  waiter, it is a cycle across nodes that only a timeout breaks. NVSHMEM's `signal_wait_until` is the type; so is
  `mesh_step_observe`.

What follows:

- The transport fills and drains and decides nothing. A SEND is postable when its producer publishes. A relay fires on
  its landing's completion. No entry holds back a later independent one.
- A data-processing function receives its landed prefixes as operands, data rather than waits. Its own source states
  its consumption pattern: the whole input, tiles in arrival order (I17's arrival-derived page indices), a mask over
  what is present, or a race it accepts. Threadgroup barriers among its own threads are syncs, and allowed.
- The scheduler fires a function's work on presence. It never launches work early to spin.
- With no wait in any kernel, no kernel can hang its GPU. The poll bound and failure claim (G2, G3 in
  send-receive-wrappings-2026-11-02.md) go with the waits, and the safety rule is met by construction.

## The page map's interface (proposed)

Chooser-visible objects carry integers and maps only:

- A page space: the region's physical pages, by page size (16 KiB on these members) and count. Pages are identities,
  never addresses.
- A page map: invocation → (virtual page → physical page). The allocator produces it as explicit runs per invocation.
  It is never a formula a person picks. Where the runs happen to be affine, the specializer finds that and emits base
  plus offset.
- A value: a typed layout (`MetalTensorLayout`: logical index → virtual element, with the scalar width) composed with
  a page map. This is a chooser's only operand: the record of a tensor, a landing, a SEND source, a progress word or a
  descriptor table.
- A lifetime: an interval over the function's event order (command ordinals, times invocations), with transport
  events in that order: post, SEND completion, landing, last read, bridge leaving a table.

Chooser operations, all pure:

- compose (a layout with a map, or a view with a value);
- image (a value at an invocation → physical page runs and in-page byte runs);
- preimage (physical runs → the logical indices of a value);
- meet (do two values' images intersect while both are live?);
- allocate (values with lifetimes → their page maps). This bin-packs in mesh-graph's interval module, consumers as
  operands.

Lowering-only operations, which no chooser file can import:

- specialize (a value at an invocation → pointer literals, or base plus affine offset, from the page table);
- bind (a specialized value → a Metal argument, an SGE, a bridge table entry).

The existing types map onto this as follows:

- `MetalTensorLayout` is the layout factor, unchanged.
- `ncclMeshPageBacking` runs are an invocation's map, written out.
- `ncclMeshPageSelection` and `Compose` are composition.
- `MeshIndexInverse` and `MeshIndexPreimage` are preimage on the layout factor.
- `ncclMeshBuffer`, `ncclMeshBufferSlots`, `ncclMeshInvocationIndex`, `ncclMeshPageTableCreate(const void*)` and
  `ncclMeshRegionRuns` have no place in it.

## Values at the program boundary

Every torch tensor of a mesh process is a lease: region pages from `ncclMemAlloc`, behind a no-copy MTLBuffer
(torch_mesh/allocator.mm). So:

- A tensor the program allocates and a declared function only reads or only writes is a value with a constant map.
  Weights, X and O are of this kind. Its map is the lease's page table, handed out with the lease at allocation. It is
  never recovered later from an address.
- A state tensor that a declared function reads and then writes is renamed per invocation. The LSTM's h, c and step
  counter are of this kind. Each version lands wherever pages are free over its lifetime, so no reuse waits on a
  reader. The allocator pins the program's lease pages only where the program touches the state:
  - invocation 0's input, which the program writes (`reset()`);
  - the last invocation's output, where the program reads the state afterwards.
- So the packer takes pinned items: a lease is an item whose place is given. It places every other item around the
  pinned ones and fails at compile time if a pinned item collides with a live one.

There is no copy-back, and the program sees its tensors as it allocated them.

## Placement onto values

Today's fixed-binding path (torch_mesh/placement.py, `Placements.solve`, about lines 185–238) is the in-place
landing in chooser form. For a family of values that alias one another (equal views) and touch a caller's tensor:

- it reads the caller pages' region byte positions (`_stream.page_domain`, `_stream.physical_layout`);
- it unites them into the family's domain and packs the family over them (`assign`, `identify`, `unite`, `rebase`,
  `choose`);
- it composes one storage for every member (`_stream.page_storage`, a remapped view).

So every version of a state, such as each tick's h, aliases the caller's lease pages. The transport then guards that
by posting receives late. The positions are also the large constants of the declaration's layout algebra (d-r3).

The replacement:

- A family's members keep layouts in the family's own virtual elements (mesh-page-map.h pieces). No region position
  enters; a caller's tensor enters as its value (`_stream.tensor_value`: a piece over its storage, its lease's runs).
- Each member is a version with a lifetime in the declared function's event order. A version's lifetime runs from
  the posting of its receive, at its invocation's start, to its last read.
- Only the versions the program touches are pinned to the caller's lease: the state's input at invocation 0, and its
  output at the last invocation where the program reads it afterwards. mesh_page_allocate places every other version
  by its lifetime.
- The result per member is a value: the family layout composed with the member's page map. A storage composed by
  remapping (`page_storage`, `mach_vm_remap` in `ncclMeshPageTableCompose`) has no place. The final lowering
  specializes values into addresses.
- `choose` (MetalTensorPlace) still assigns the family's virtual elements: typed fields, alignment, demands. It works
  in the family's virtual space only.

## Where the versions live

One realized run is one `page_effects.Plan` over the whole flattened sequence (declarations.py, `append`): the input
broadcast, the starting ticks, then the tick function's steps once per tick. With one tick a replay, a run's eight ticks
are eight occurrences of one declaration, each binding the same `self.h` storage. So:

- The versions of a state are per occurrence within a run, and the Plan is where their lifetimes are known: from the
  write that lands a version to the last read of it by a later occurrence.
- Today the out= collective into state is declared as an effect on the section's own input field ("its pages are the
  result's", declarations.py about line 852). In the joint form, the result is that state's next version: an output of
  the section, not an effect on its input.
- Kernel source is already shared across occurrences ("repeated uses of this exact retained numerical declaration
  share its emission", page_effects.py). Only an occurrence's operand bindings differ, and they are argument-table
  entries.
- The interval packing gives every allocated value one consecutive run of physical pages. So the specialization of an
  occurrence's operand is one pointer literal into the region: its base, plus the first page times the page size,
  plus the in-page offset. A kernel indexes it affinely, as hand-written code would. There is no page table at run
  time.
- Program leases are pinned items with their own runs. A lease of several physical runs is specialized run by run.

A version is per occurrence, not per functional operation. Functionalization runs without input writeback here
(compilation.py: `mesh_input_writeback` False), so a state's mutation arrives as functionalized base pairs
(`_collective_results`' `preserved`: source, result, writes). The LSTM's tick writes h twice:

- the cell writes this rank's slice through `mine`, a view of h: base h1, every other position preserved from h;
- the gather lands the peers' slices into h1: base h2, this rank's slice preserved from h1.

h1 and h2 are one new version assembled within the occurrence, on the same pages. Only the occurrence's input, h, is
a different version. The rule:

- a state gets its new version at its first write in an occurrence, and later writes there go to the same version;
- positions no write of the occurrence covers keep the old version's values. A page none of them touches maps to the
  old version's physical page, so it costs no copy. Only a partly written page carries bytes over.
- For the LSTM nothing is carried: h, c and the step counter are each written whole every tick.

The order of work in the frontend: the section's state outputs (declarations), then the Plan's per-occurrence
lifetimes and mesh_page_allocate, then per-occurrence argument bindings in the recorder through mesh-page-lower.h.
Placement's fixed path follows, then page effects' relations over values.

## The interface that carries it

`placement.selected` binds a span's fixed records to the caller's storage, the state's read use and its written
use alike: `placements.bind(root, TensorView(actual.storage_as(uint8), target))`. Everything downstream consumes that
object. `TensorView(storage, layout)`, a layout over an actual torch storage, is what page effects (`describe`,
`bind`), the native bind (`PageEffectsPlan`), `_stream`'s Metal bindings and the recorder all take. Placement runs once
per declaration, but versions need pages per occurrence. So no local edit to placement carries them: the interface
changes.

- `TensorView(storage, layout)` becomes a value: a layout over the value's own virtual pages, with its map supplied
  per occurrence by the run's Plan (mesh_page_allocate) and specialized only at the final lowering.
- A caller's tensor enters as a value with a constant map (`_stream.tensor_value`), pinned where the program touches
  it.
- Consumers move in this order, each in full:
  1. placement (`selected`, `Placements.solve`);
  2. page effects (`describe`, `bind_effects`, the native bind's accesses and reaches: relations over a value's
     virtual elements);
  3. `_stream`'s chooser module, which holds values and layouts only. Its lowering module holds `tensor_value`'s
     inverse, Metal bindings and storage handles;
  4. the recorder's per-occurrence argument bindings (mesh-page-lower.h);
  5. the collective lowering in nccl-mesh.c (`ncclMeshBuffer` leaves its chooser records; spans come from
     mesh_page_sges at the final lowering).

## Page effects onto values, and when pages may be reused

Today every access is keyed to one region root, with relations over region bytes. `page_effects._physical` asks
`_stream.page_region`, which computes them from `buffer.contents` and offsets. Those are the large constants in page
effects.

- Each space is its own root. A command's accesses are relations over its operands' virtual bytes, shared by every
  occurrence of its emission. Constants stay small: a space's extent, never a region position.
- Two spaces never alias while both are live, because the allocator gives overlapping lifetimes disjoint pages. So the
  solve need not see physical pages to find a hazard.
- Reuse is safe only along causation. The recorder emits no barriers, so launch order guarantees nothing. A page passes
  from one value to the next only where the old value's last access happens before the new value's first access in
  the data-dependency order: a chain of true reads after writes. The packing's interval order is therefore a
  happens-before order, not the program's total order. Where no causal edge exists, the pages are not shared, which
  costs memory and no wait.
- The LSTM has the causal edges. h(t+2) may take h(t)'s pages because its writers causally follow h(t)'s last reader,
  the products of tick t+1: the cell of t+2 through t+1's outputs, and the peers' landings through the h(t+1) pieces
  they wait for.

## A kernel's effect fields

Besides its operands, a generated kernel reads and writes effect fields: progress words in leases, `landed` words in
stream records, threshold tables and activity masks. Today `MetalPageFields` collects them and `compose` maps all
their pages into one remapped view (`ncclMeshPageTableCompose`, `mach_vm_remap`). So a kernel reads
`mesh_effects + 3272ul`, a word's place in a composed view of foreign pages, fixed at preparation. Choosing and
lowering are mixed in one native bind: the bind returns `reaches` as buffers, offsets and pages.

Metal 4 binds by GPU address (`MTL4ArgumentTable setAddress:atIndex:`), so no composed view is needed:

- The native bind, a chooser, returns each command's fields as values with an offset (a word, a table, a mask) and its
  threshold tables as integers. It allocates nothing and returns no reaches.
- The final lowering writes one small table per occurrence: a GPU address a field, the region buffer's `gpuAddress`
  plus the field's offset in that occurrence's pages. These are the pointer literals.
- The kernel loads each field's address once at its entry, then dereferences it.
- The remap and its page-table composition have no place.

## The run's page assignment, in order

1. Tag each flattened step with its function invocation. `Executions.append` flattens functions' steps and loses
   their boundaries today; the tag gives each occurrence its items.
2. Solve page effects first. With a root per space the solve needs no physical pages, and its observations are the
   true read-after-write edges between commands.
3. Allocate. The items are (space, invocation). An item begins at its invocation's first access, or at the
   invocation's first step for a landing destination, whose receive is posted there. It ends at its last access.
   `settled(k, l)` is reachability over the solve's edges: k's last access is an ancestor of l's first. The program's
   step order is never used for this. State spaces are pinned to their lease where the program touches them.
4. Lower. Each occurrence's operands and effect fields are specialized through its maps (mesh-page-lower.h) into
   pointer literals in the recorded commands.

Then `_stream` splits by role: the steps above that hold addresses (recording, schedules, pipelines) move into the
lowering module, and the chooser module keeps layouts, values and the solve.

## Construction

The change is built whole in one worktree. It lands on main as one series once the entire collective runs it end to
end. Nothing runs or lands half-built.

1. The page map. One representation: invocation → (virtual page → physical page), composed with a typed layout
   (logical index → virtual byte; the scalar width enters only at the final lowering). Its operations are compose,
   inverse, image, preimage, meet over lifetimes, and specialize at an invocation. It absorbs `TensorLayout`,
   `MetalTensorLayout`, `MeshIndexInverse` and `Preimage`, `IndexRelation.through`, page-table composition and backing
   runs. `ncclMeshLayout`, page selections and backing runs already have the target form. Graph and interval
   algorithms in it live in mesh-graph.h and mesh_graph.py, with consumers as operands (rubric C9).
2. The allocator. Lifetimes come from the declared function, transport included: a SEND's source until its `sent`
   prefix covers it; a landing from its invocation's start, when its receive is posted, to its last reader; descriptor
   tables until the bridge leaves them. Pages are bin-packed across invocations by these lifetimes and returned through
   the retire ledger (rdma/mesh-lease-retire.h). No ring, no slot, no fixed generation.
3. Chooser scope. rdma/nccl.h and torch_mesh's `_stream` split into a chooser part (page maps, layouts, constants) and a
   lowering part (addresses, Metal bindings, storage handles). Chooser files cannot import the second. `ncclMeshBuffer`
   leaves every chooser record. Records are ordered by declared identity, never by address.
4. The final lowering is the one pointer producer. For each realized invocation it writes pointer literals, or a base
   and an affine offset, into recorded kernel arguments, SGEs and bridge tables. No kernel evaluates a map.
5. Transport. Every link goes at its invocation's start (T2). SEND lists are not gated by the link (T3). Relays fire on
   completion, and `after` lists go: renaming removes T11, T12 and G6. In-flight capacity is proved at compile time,
   replacing the run-time frame and request tests (T5). Static tables name no spans word (T4a). One chained post per
   lane per pass replaces the 64-unit budget (T14). Region offsets stop crossing sockets.
6. Consumers. Landed prefixes become operands. Guards are written in each data-processing function's own source. The
   in-kernel waits go. The firing-on-presence mechanism is settled from shipped binaries and XNU and Metal sources
   before any probe: a command-queue wait on an event the bridge signals, a CPU commit, or a resident worker over a
   ready queue.
   What the shipped binaries say so far (macOS 27 dyld shared cache, read with ipsw, 2026-11-02):
   - `MTL4CommandQueue waitForEvent:value:` (public) holds the queue's later work in the command processor. No core
     spins. A compute encoder has no event wait, so firing on presence is at command-buffer granularity.
   - `-[IOSurfaceSharedEvent setSignaledValue:]` is one IOKit trap: `IOConnectTrap2(connection, 7, eventID, value)`.
     There is no message and no method-call marshalling.
   - Its getter is two plain loads from a page mapped into the process, which the kernel side also writes.
   - `_MTLSharedEvent` wraps that object (`-[_MTLSharedEvent IOSurfaceSharedEvent]`). It also offers
     `initWithMachPort:` beside the public handle that is passed over XPC.
   - `MTLCommandQueueDescriptorInternal` has a private `enableLowLatencySignalSharedEvent`. It is not public API; it
     only shows that the driver distinguishes a low-latency signal path.
   - Open: what trap 7 does inside IOSurface.kext to wake the GPU's command processor (the kernelcache, next).
7. Programs. examples/lstm.py keeps one `h` value a tick, `out=` read as a value definition. torch_mesh/chain.py's
   two generations go. examples/lstm-service.py's broadcast of X into X and examples/chain.py's fixed scratch window
   go.
8. Acceptance. End to end on every live node: the LSTM at 8 and 64 steps, the chain service, then the trainable LSTM.
   Report per-case rates (µs, GB/s) against their bands, and the LSTM's step against plain Metal's 31.5 µs on one
   Studio.
