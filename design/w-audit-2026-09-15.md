# W audit — withholding work, storage and execution flow

This audit follows the operator correction in [deliverables.md](deliverables.md):
I18 prohibits guards and blocks that prevent values from being drained or
transacted. Dedicated queue polling, indexed page placement, native completion
handling and the declared dependency countdown are permitted. A conditional or
page-table load is not by itself evidence of an operation wait.

The former blanket polling/indexing prohibition and its proposed immutable-address
replacement are superseded. The indexed-address correction applies to mesh `b1703a3` plus native error
normalization `7c7fee4`. ABI 48 subsequently replaces publication notices as
described below. No runtime speedup is established by that replacement. W1–W6 remain open for the specific reasons below.

<a id="w1"></a>

## W1 — publish path

`mesh_call_complete` publishes declared output rows, then releases completed uses.
`mesh_publish` updates presence and walks fixed numerical/link use bitmasks. Those
are indexed dataflow operations. The remaining defects are its callees:

- `mesh_notice_push` now performs one release OR per realized bitmap level.
  Readers exchange and enumerate indicated words; there is no CAS retry, reserved
  queue position or linked entry. The [proof](pages-and-functions.md#publication-notifications)
  covers simultaneous publishers and delayed summary updates.
- `mesh_buffer_release` enters `mesh_buffer_enqueue` at refcount zero; enqueue has
  a duplicate claim check and another CAS retry stack.

X1 removes the notification stack; X5 must still replace reclamation. Publishing a
value must not wait for delivery,
a consumer, or another publisher to finish. Refcount zero is an ownership event,
not a caller free protocol.

<a id="w2"></a>

## W2 — receive path

`link_progress` owns one thread per link and direction. `mesh_progress` polls one
native completion per queue and attempts another receive before publishing that
completion. Native refusal leaves the post cursor for the next progress pass;
there is no software outstanding-frame admission gate. A native error concludes
the affected invocation out of band. The sticky receive-failure guard is removed.

Setup allocates distinct receive runs for each queue. The completion identifies
the physical page; the source chunk tag is interpreted in that queue's prepared
source-to-target table. `mesh_receive_assign` associates the logical row with the
actual backing. Its forward/inverse table updates copy no payload. Disjoint queue
runs keep RX threads from editing the same placement entries. Finite posting uses
each physical slot once; later assignments cannot displace a published page.
See [block addressing](pages-and-functions.md#block-addressing).

These mappings are required mechanisms, not violations. W2 remains open because
publication still enters the W1 reclamation path, the receive list is finite, and general chunk
interleaving/striping needs the X3 contiguous-operand path.

### X3a receive matching prerequisite

If receives are posted at a then b, B may arrive first at a. The page table then
names a as B's backing. A arriving at b names b as A's backing. Consumer identity
follows logical rows, not receive ordinal. Both producers may publish immediately;
there is no requirement for one native QP per independent value.

For multiple peers, source row identifiers are interpreted within each peer/link's
prepared transfer relation; equal source integers from different peers are not
the same value. Interleaving completions from the two neighbors of a ring does not
require a shared completion order. Every logical value retains its actual backing
through its own declared readers and transfers.

The remaining prerequisite is layout representation. Current code sends each
section's chunks consecutively per queue and binds one contiguous receive window.
A table can represent a fragmented section, but that fact alone does not make a
single base-pointer/byte-count operand contiguous. X3 must supply suitable sections,
supported aliases, or asynchronous placement into canonical operand storage.
Only the consumers of that placement depend on its completion; unrelated queues
and consumers continue. Payload movement, when required, must be accounted for.

<a id="w3"></a>

## W3 — send path

`link_publications` enumerates notified row bits, uses a prepared row-to-send range
and appends the ready send indices. `link_send_ready` resolves the current chunk page
and posts it. Page resolution is legitimate. The finite append-only ready array, reclamation stack and absent traversal rearm
remain unfinished.

Native queue refusal is the admission limit. Empty-queue observations do not wait
for a particular tensor. A pending request must not stop other links from draining.
The current per-queue consecutive-chunk policy supports contiguous receives;
changing it requires X3 layout support, not a caller-visible transport restriction.

<a id="w4"></a>

## W4 — submit path

`mesh_calls_submit` publishes root rows through the indexed notification bits. It has
no operation wait or allocation, but still lacks N1's reusable instance allocation
and immediate busy result when the free pool is empty. The finite index range is
not an unbounded invocation API. X1 has removed the notification stack; X5/N1 must
provide completion-driven reuse without modulo selection of an occupied slot.

<a id="w5"></a>

## W5 — result and reclamation

`Mesh.result` performs one status load. Declared numerical and transfer references
prevent success before those uses finish. There is no link scan in this path.

Reclamation still uses `mesh_buffer_enqueue`'s claim check and CAS stack.
`mesh_collect` follows linked entries, defers device-owned closed buffers, resolves
actual pages and clears bitmap allocation bits. Page resolution is valid; this
queue/allocator is not the required X5 instance free pool. Removing it requires
preserving native device and numerical ownership, including early teardown.
N1 cannot reuse storage just because its submission index wraps around.

<a id="w6"></a>

## W6 — invocation path

`mesh_call_progress` drains notices and walks prepared consumer ranges, decrementing
pending counts. Zero submits the supplied function. It never scans functions for
input presence. ABI 48 removes the notice list: `mesh_notice_take` enumerates only
pending bits using reader-local arrays, returning on an empty root.

`mesh_call_submit` updates remote entries of its allocated operand array from the
canonical page table. `MeshBindings` selects already prepared native views using
the resulting page index. Both implement the intended logical/physical separation.
Core ML's feature-provider protocol requests values by name; its lookup is native
interoperability to minimize, not a reason to invent a second model interpreter.

The remaining integration work is reusable native launches, fragmented/contiguous
layout handling, and preserving storage through backend completion. Metal command
buffers are currently prepared once and committed once. No N1 rearm exists.

<a id="w7"></a>

## W7 — collective compositions

All collective verbs are declarations over sends and supplied functions. Explicit
owners, destinations, routes and combine functions are realized before execution.
T2 expands a route into sends of the same received section at each relay. No route
lookup or model interpretation occurs during transport. Collective semantics do
not depend on world size or arrival order. Existing runtime defects still apply
to the realized edges.

<a id="w8"></a>

## W8 — caller bindings

The Gram caller's supplied Accelerate operations return after producing their
outputs; their library dispatch/publication paths inherit W1–W6. This is source
composition, not evidence of distributed speedup.

Engine `769567d` and `aad2874` added copied prompt storage, host-polled stamps and
an implicit `encodeWaitForEvent(prefillDone)` in embed. `74a62ff` removes them.
The I18 clarification does not permit that wait: prefill must publish operands
consumed by decode through declared dataflow. The remaining engine attention
binding still reaches the host `attentionSplits` scan. In `lm_engine.swift:1909`,
`encodeWaitForEvent(graph.meshStepEvent, ...)` also precedes `encodeDecodeOutput`.
That implicit output-stage wait remains an E3 defect: bind output processing as a
consumer of the Mesh-produced operands instead of deleting the wait while leaving
an undeclared read. W8 is partial pending those integrations.

The concurrently integrated public report
`metal-microbench/output_data/mesh_e3/compare_A_8x8.out` reports inferior two-node
decode at engine `772a8cb` / mesh `7c7fee4`. It is performance evidence against E3
completion. The launch-granularity and host-staging explanations in rows E1c/19k/19l
are implementation work to investigate and fix, not a page-table impossibility.

## Implementation order

1. X1 notification replacement is implemented in source. W1 remains open through
   reclamation; retain the single-publication/declared-ownership contract during reuse.
2. X5/N1t/N1: turn final declared ownership into free-pool events; rearm transport
   and native launches for the next instance without occupied-slot selection.
3. X3a/X3/T3: retain peer-qualified indexed receive matching; complete interleaved
   chunk placement, contiguous backend operands and multi-link striping together.
4. N2/E3: complete recovery and prefill-to-decode dataflow, then exercise the public
   chain using the existing measurement path. No documentation correction or
   compilation substitutes for the required speedup evidence.

ABI 48 validation: the C sources pass compiler diagnostics; the bridge, Mesh
module, existing Core ML/Gram/indexed/sync callers and engine Mesh target build.
The compiled publication path uses `ldsetl` and notification dequeue uses `swpa`;
the removed CAS loop is not recreated by those atomic operations in this build.
No runtime experiment or speedup claim accompanies this source change. Reclamation
still has its separately recorded CAS retry.
