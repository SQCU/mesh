# Who chooses a matrix implementation? Review of 23 November 2026

The reference operation is `C = A @ B`. For a column partition a worker reads `A` and its columns of `B`, computes those columns of `C`, and writes the assigned result extents. Input ownership specifies whether a worker already has `A` or receives it. The bridge takes destination node and page indices and owns physical routing. The [composition request](compilation-composition-change-request.md) puts numerical and communication choices in IR before final lowering. The [shard request](unequal-shards-change-request.md) supplies counts, displacements, views and cost operands.

**A:** In metal-microbench `d8061ad9`, project code converted a named PyTorch matrix multiplication to a generic multiply-and-sum region. `RecognizeDense` recovered the contraction. `TensorMatrices` called `MatrixLayout` on both inputs and the output. Its stride reader, introduced for CPU Accelerate in `9ac02964`, returned false on a paged root before composing the strides. `NativeMember` then emitted the older SIMD-group matrix kernel. Both kernels compute the product. Output equality therefore hid the lost implementation choice. The emitted source hashes identified what ran.

**B:** The matrix constructor supplies its known axes and original operand views. The target computes which implementations can consume those views and reports the selected implementation on the originating operation. The allocator supplies the physical pages. The target binds those pages through a frame mapping or a contiguous virtual view, as required by the chosen instruction. The final writer emits that instruction. Anonymous contractions may still need pattern recognition. CPU Accelerate's flat-pointer calling convention applies at the Accelerate call.

### Who authorized fusion?

**A:** Compiler-emit passed the numerical program to `program.construct(device)` after attaching issue groups and dependency relations. It omitted the requested rewrite. Metal's `ConstructionRewrite` interpreted that absence as `METAL_IR_ALL_FUSIONS` and ran the optimizer inside construction. The caller lost the ability to choose an unfused implementation of the same scheduled graph through that interface.

**B:** The caller supplies the scheduled graph and the fusion choice for a candidate. The numerical rewrite reads those operands and writes its surviving operations, groups, access relation and materialized byte sizes. The constructor reads the resulting program. Selecting zero explicitly retains the unfused alternative. Metal commit `fd991b65` removed the implicit optimization from both constructors and updated the standalone callers. Native-execution `5553f55` and compiler-emit `a773b95` apply the rewrite to the candidate's derived program before construction.

The existing Metal GPU evaluation provides a case where the distinction changes the physical program. With the same input IR, choice zero yielded two operations, two groups and 512 temporary bytes. Choice seven yielded one operation, one group and zero temporary bytes. In the public FX six-linear-layer example, both choices yielded thirteen groups for this input. Fresh and reopened Metal images for both choices returned the reference result within tolerance on three changing inputs. Calling the constructor on an unrewritten program returned `EINVAL`. These observations refer to the revisions above.

Metal `62ed94fb` and compiler-emit `c493cbe` make the same distinction for each named matrix product. The caller supplies an ordered set of candidate implementations for that operation. The target rewrite checks each candidate against its typed operands and records its mapping. Numerical construction reads the mapping. A six-product FX model used different supplied orders on alternating products. Fresh and reopened images agreed with the reference within a maximum absolute error of 1.05 × 10⁻⁷.

### Who orders two independent readers?

**A:** Compiler-emit's `MetalRows` constructor projected the solved dependency graph onto commands, computed a priority for each command group, and called another constructor that ran the dispatch solver. It supplied two answers for the same choice. One was an unsigned rank inherited from the default order. The other came from the caller's weighting function. `MetalIssueOrder` used the rank whenever its array was present. In a two-reader program the ordinary weighting and a weighting that favored the second reader both put that reader's last command in position seven.

**B:** Compiler-emit `6905e7a` projects the selected graph onto its command groups once. The caller's weighting function reads those groups and their positions in the solved graph. Metal `66f5bf91` passes the resulting weights and the dependency edges to `mesh_graph_heap_order`. The installer takes that schedule as an operand. An image loader restores the schedule from its serialized positions. The standalone compile-and-record entry computes a schedule from its own supplied rows. In the same two-reader program, the two weightings now put the second reader in positions seven and three, respectively. The evaluator checked every zero-delay edge against each order.

The dated timing files and per-rank logs are in the companion compiler-emit repository under `artifacts/fleet-matmul-20261123/`. The implementation landmarks above refer to those revisions.

Compiler-emit `b932220` records two measured-choice comparisons of a full 1024 × 32768 × 1024 FP32 product, with replicated input and gathered output. Four M5 Ultras took 1.726–2.008 ms at 38.86–42.70 useful TFLOP/s. The fastest single eager MPS results across the five machines were 3.400–3.407 ms at 21.39–21.40 TFLOP/s. These runs preceded the explicit rewrite requirement. Separate same-shape per-GPU trials still showed a throughput deficit on two of four GPUs. A separate irregular two-node SIMD-group run sent an old result page before the GPU finished writing it. The returned tensor failed its numerical comparison. Its timing contributes to none of the figures above.
