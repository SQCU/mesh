The first native RDMA validation did not reach eight updates per policy. Its evidence is preserved in `rdma-runtime-before-receive-fix.json`, `rdma-runtime-before-receive-fix.log`, and `rdma-1788744399507754000/`.

The responder previously drained `Mesh.read` until the native receive ring became empty before considering a complete snapshot. `Mesh.read` repeatedly overwrites one array of 1,024 borrowed frame views. Consuming each view immediately fixes its lifetime, but an unbounded sequence of full batches can still postpone policy execution indefinitely under sustained production. The synchronous matrix RPC receive loop had the same problem, including delayed cancellation and deadline checks.

`Mesh.read` now accepts an optional batch limit. The responder and matrix RPC consume exactly one complete native batch before reconsidering work. They never stop midway through an already borrowed batch. Other callers retain the previous default behavior. The isolated datagram validation adapter implements the same scheduling contract.

Twenty-five receive, event-memory, continuation, and scale-RPC tests passed on both the laptop and Mini. The tests include a producer that never returns an empty batch, complete snapshots and all 1,020 event frames in each 1,024-frame batch, a large STATE message spanning batches, and completed RPC responses surrounded by continuous unrelated traffic whose backlog remains valid after buffer reuse. Only application Python files were staged to `runtime-representation-20260906`; no test attached to `/mesh0` or altered a bridge.

This correction does not establish lossless delivery. The failed run repeatedly discarded incomplete STATE assemblies while smaller OBSERVATION, CART, TEAM, and EVENT frames completed. At request 284, for example, STATE had 12,146 of 12,866 frames, 2,300 rejected fragments or incomplete assemblies, and 260 resynchronizations; the responder still had only six responses. Native publication copies complete snapshots into an append-only FIFO (`meshx_publish`, `pending_push`); it does not replace an active STATE transfer.

The failed run's bridge deltas report 2,999,261 laptop frames sent and 2,824,142 Mini frames received, a difference of 175,119, with `bad=0`. The inspected `mesh-flow.c` releases incoming pages when the completion ring cannot accept another descriptor, and that path does not increment an explicit drop counter. Its completion ring has 65,536 entries; policy preparation, inference, optimization, and checkpoint writes all share the application's receive thread. This is a source-level loss mechanism, not a demonstrated cause of the failed run. Native STATE frames have no message replay mechanism, so actual missing fragments skip a snapshot rather than merely delaying its completion. Complete EVENT frames retained by `RuntimeFrames` survive application snapshot coalescing; event fragments lost before reassembly are a separate transport boundary.

The operator subsequently confirmed that another session was actively changing distributed mesh primitives and reductions during these validations. Bridge PID changes occurred concurrently. The failed large RDMA runs therefore do not establish the failure cause of a stable final backend, and before/after aggregate counters cannot distinguish completion-ring loss, application pauses, and concurrent backend changes. The bounded-receive tests establish application scheduling and borrowed-buffer correctness independently. Final native feature and continuation validation uses only the isolated socket transport; no additional `/mesh0` load or bridge changes are part of this task.

The failed engine log also records `GetResourceLimit: Invalid resource type` bot-view faults, with invocation unwind and stock behavior recovery. The earlier isolated native validation had zero view faults. This is a separate actual policy-application failure and must not be hidden by a transport-only explanation.
