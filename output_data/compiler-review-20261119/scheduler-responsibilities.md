# Scheduling repeated sharded calls, 19 November 2026

## The input program

`A(x,w)` multiplies an 8 × 16 matrix by a shared 16 × 32 weight. `B` takes ReLU. All shapes and calls are fixed. The three inputs to A vary independently.

```python
p = A(x, w)
q = B(p)
r = A(y, w)
s = B(r)
t = A(z, w)
return q + s, t, q[:, 1:29:2]
```

A owns 24 columns on one processor and eight on the other. B needs 16 on each. Both B results feed the sum. The strided output also reads the first B. The comparison first supplies a direct link and then compiles a topology on which every transfer between the numerical processors takes two hops. In a second program, a call updates the shared weight after the first multiply. The next multiply reads through the original argument, and the third reads through the updater's result. The caller observes the weight after return. The existing sharding client runs both programs with `--call-bounds`. [Executable inputs and comparisons](../../../../compiler-emit/artifacts/joint-sharding-20261119/evaluate.py)

## A: What the earlier implementation did

For the seven calls above, the partitioner made twenty physical calls and supplied twenty distinct function numbers to the native scheduler. Both the bound-one and bound-two programs returned the right tensors on three inputs. The bound rows constrained twenty different functions across iterations. They omitted the constraint between successive invocations of A in the same iteration. Two other substitutions lost information at the same boundary. An explicit fusion of the first and third updates in `add_(1), mul_(2), add_(1)` moved them across the multiply and changed 7 into 8 for input 2. A right-hand worker that needed a view of the caller's weight received an unbound operand even though its input table already held the backing tensor. [Prior scheduler trace](../../../../compiler-emit/artifacts/joint-sharding-20261119/source-call-bounds.md) · [Source and substitution](../../../../compiler-emit/compiler_emit/source.py)

The communication graph also chose the first rank as owner of a transfer-free function. Its rank-work vertex took its duration from the transfer geometry. Changing the duration or placement of purely numerical work could therefore leave a zero on the wrong rank. The queue target could emit two independent calls in one Inductor compilation while omitting the selected source issue constraint. A delayed first worker and a quick second worker then completed in reverse order even with a limit of one. ## The changed program

The compiled family rows now read `A, B, A, B, A, add, slice`. The three A occurrences use the same weight and keep distinct completion events. With limit one, the first A releases the second A in the same block. With limit two, the first A releases the third. With limit four, the third A releases the first A two blocks later. B can have its own limit. On both numerical ranks and the relay, a fresh archive load reproduced the complete source and projected physical constraints. In each placement the two compiled CPU workers matched eager Torch on three inputs. The mutation variant also reproduced all three matrices and the caller's final weight. [Recorded run](../../../../compiler-emit/artifacts/joint-sharding-20261119/source-bounds-execution.txt)

The source partitioner accounts for the original storage conflicts before grouping calls. The planner retains numerical site and duration through the per-rank work graph. The target reads the source-bound edges from the analysis. On one worker, the strict limit added an Inductor dependency between two independent numerical kernels. On two workers at one Mesh rank, the strict limit added a queue between the calls. Raising the limit let the quicker second call finish first. The reference execution used local CPU workers. The relay observation exercised compilation and archive loading. These runs measured no physical-link latency.

The mutable weight also ran from offsets 3, 7 and 0 in its input storage after capture at offset 3. Across these calls, the maximum error was zero for each output and for the caller's weight. Numerical rank durations also changed with resource placement. Two independent operations priced at 3 and 7 on rank 1 gave 10 on a shared resource and 7 on separate resources. These are costs in the units the caller supplied. ## A: Each function priced its own work and the recorder imposed call order

For two independent branches, `A(x) = exp(cos(x))` and `B(y) = abs(sin(y))`, both local schedulers gave their first operation completion time one. Each solver saw only its own head on the shared processor. The native emitter also projected FIFO delivery of calls onto GPU command order. It issued A first even when B had the longer dependent tail. Upstream numerical fusion could bind a head to its tail before the other branch got its turn. Correct return values survived all three mistakes. ## B: Solve across the call graph and issue each resource’s selected work

The compiler expands each distinct body into numerical instructions and routed hops. It gives each occurrence its own interval in the whole-program graph. Placed reads and writes name the instructions that intersect at a shared byte range. The scheduler adds the rank-local issue constraints and prices each actual device and directed link. One completion-time model and one heap order give the instruction positions for every occurrence. Before routing, the compiler estimates capacity from source calls. Once routing supplies the hops, the allocator reads the whole-program graph’s cross-call edges, resource cycles and block distances. The emitters read the positions of the instructions they implement. A debugger counted two body expansions, one invocation of the completion solver and two projections for the two-body client. The solver performs the two objectives and the resource-cut iterations specified by R5. [Single solve and exact page edges](../../../../compiler-emit/artifacts/joint-sharding-20261119/whole-program-completion.md) · [Native cost and capacity](source-issue-and-rank-time.md)

With unit-cost heads on a shared resource, pricing the tails at 10 and 1 selected `cos → sin → abs → exp`. Swapping only those prices selected `sin → cos → exp → abs`. Torch and Metal fused the neighboring pair in each order. Metal therefore issued A–B–A in the first case and B–A–B in the second. The saved schedule stores the completion graph, costs, resource identities, per-occurrence positions and block-distance edges. Opening the executable reads its command order and binds its buffers for another call. [Kernel orders](../../../../compiler-emit/artifacts/joint-sharding-20261119/torch-completion-emission.md) · [Metal, peer and archive observations](../../../../compiler-emit/artifacts/joint-sharding-20261119/source-bounds-execution.txt)

For an 8,192-element result split across two pages, the first landing released the sine of the first 4,096 elements. The second landing released the cosine of the other 4,096. On the seven-call program, the direct topology produced 227 scheduler vertices. Selecting two-hop routes produced 262. The graph retained sixteen cross-call instruction edges in both cases. Both endpoints of every directed hop compiled the same posting sequence. The relay owned ten local transfer records and ran no numerical kernel. These comparisons exercised modeled links and local CPU and Metal execution. A second input distinguishes a function’s declaration from the order of its separate invocations. Let `split(x)` return both `sin(x)` and `cos(x)`. One downstream call reads the first invocation’s sine. Another reads the second invocation’s cosine. The previous Metal emitter issued the first invocation’s two parts, then the second invocation’s two parts. The scheduler had selected sine₀, cosine₁, cosine₀, sine₁. The emitter now projects the selected instruction edges onto the commands that implement their endpoints. Each call has distinct submission, entry and completion events. Its completion follows all its work, whichever part issues last. Fresh and reopened Metal programs both issued the four operations in the selected order. In a single invocation, an exponential that read the sine ran before the independent cosine. Every returned tensor agreed with eager Torch on two inputs per program.
