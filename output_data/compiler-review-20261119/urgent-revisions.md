# Urgent compiler revisions, 19 November 2026

Review of Mesh `72f7a4db`, compiler-emit `1cf163d`, schedule-emit `25891ea`, native-execution `9790fd5` and metal-microbench `3d1508a6`.

## A: How a successful run conceals missing work

The same tensor values can come from a 512-byte plan and a 3,072-byte plan. Two targets can agree because both received the same unnecessary gather. An evaluator can also make the right tensor arrive by copying it itself. In each case eager Torch answers the numerical question. Agreement alone leaves open who chose the placement, who moved the bytes and what the transfer cost. The integration request already assigns each transformation to a producer and relates its output to the next consumer. ## B: Urgent revision queue

1. **Compose intermediate partitions across calls.** `program_operands` wraps each callee in a standalone FX graph and asks `analyze` to place it. In the comparison, the placement operand requests a whole left-hand output for every such graph. `place` has already computed each shard's extent and processor. Its return code gathers that result, then `call_accesses` names one processor as the writer of the fresh tensor. Compose the producer's shard extents with the next call's reads while the joint planner can still choose their placement. Apply the application's requested layout where the outer graph returns the tensor. For the fixed 24/8 split of `relu(x @ w)`, this admits zero inter-call bytes and a 512-byte final gather. A consumer that changes the split to 16/16 needs a 512-byte reshard and a 1,024-byte final gather. These are planner payloads. The one-call wrapper already exposes a second symptom. It has the same 512-byte demand as the flat graph, yet whole-program Torch emission stops at its single-processor check. Revise this direct consumer with the producer. 2. **Account for what the selected fusion changes at emission.** The sharding evaluator adds `region_price * regions` to the cost, where `regions` counts selected source regions. Source substitution extracts FX submodules. Metal preparation reads those modules and the target then calls `fuse` for either choice. Follow the selected operations into that target rewrite when assigning it credit for a saved dispatch, wait or transfer. A caller can price source regions directly. Physical savings need evidence at the instruction or transfer that changes. 3. **Take the saved callable's bindings from its page extents.** The Metal replay evaluation calls `compile(selected, …, archive=path)` with its original live selection. The archive branch reads the saved target programs and passes the live dispatch schedule to the recorder. For an outer graph the callable also reads argument and output bindings from the live source signature. This exercises kernel reload and rebinding to fresh buffers. A9 assigns the schedule and bindings to the saved program. Read them by view and bind the caller's live addresses. The caller controls how long those extents live. ## Implementation on 19 November

1. Mesh now partitions the outer numerical graph before inserting transfers. The compiler keeps separate call occurrences, binds their readers to the selected shards, and uses the existing reshard operation when extents differ. The reference target emits the selected calls on each participating processor. A 24/8 producer and reader now demand 512 bytes in total. Changing the reader to 16/16 demands 1,536. Explicitly requesting whole intermediate returns still exercises the more expensive plans. [Placement and execution](../../../../compiler-emit/artifacts/joint-sharding-20261119/placement-execution.md) · [Reference emission](../../../../compiler-emit/artifacts/joint-sharding-20261119/whole-program-torch.md)
2. The fusion comparison prices the recorded dispatches and directed transfer bytes. All ranks share one choice. Zero and two source regions give the same score for each of the three compared routes and splits. In the 24/8 case their kernels put the release on the writer and the acquire on the reader in both forms. These are structural readings with supplied weights. [Dispatch and transfer records](../../../../compiler-emit/artifacts/joint-sharding-20261119/fusion-dispatch-cost.md)
3. A separate process now opens the Metal program and its binding tables from saved bytes, binds live addresses and calls the program. Two installations held independent mutable state and preserved returned aliases. Older recordings can use their original caller bindings. [Saved callable, page ownership and execution](../../../../compiler-emit/artifacts/joint-selection-review-20261118/saved-callable-20261119.md)

The whole-program Torch run also exposed an ordering error that a numerical comparison had missed. Two workers appended to a shared list in the order `[1, 0]` when the first worker took longer. The joint plan now identifies the remaining effect edges after accounting for the selected tensor transfers and each worker's order. The emitter binds those edges. Both workers then appended in the source order `[0, 1]`. When the second call also read the first call's tensor, its one transfer queue supplied the required order. [Two-worker effect observations](../../../../compiler-emit/artifacts/joint-sharding-20261119/whole-program-torch.md)

**Open for repeated sharded calls.** With an outstanding-call bound of one, the second invocation of `A` in `A, B, A` must wait for the first `A` to complete. After sharding, one source invocation spans several physical calls, and a shared preparatory operation can serve both invocations. The current native interface takes one function-family number per physical call. In the recorded example it advances each of nine pieces to itself in the next iteration and loses the within-iteration bound between the two source invocations. The compiler retains the occurrence-to-piece correspondence. The native scheduler still needs to consume it when connecting completion to the next permitted submission. [Original and sharded successor tables](../../../../compiler-emit/artifacts/joint-sharding-20261119/source-call-bounds.md)

## Which observations distinguish the implementations

- **Fusion on one Mac.** Using the existing sharding evaluator, hold the graph, 24/8 split, direct route and target options fixed. Select `((.75, .25), False, False)` and then `((.75, .25), False, True)` on each rank. The selection count changed from zero to two. Both runs matched eager Torch. All five left-rank and two right-rank Metal kernel source hashes matched their counterparts, as did issue order and recorder counts. The recorder reported unknown synchronization for four kernels in each run. These observations leave both legal convergence and a lost distinction possible. They measure neither elapsed time nor a physical link. [Recorder output](fusion-emission.txt) · [Hash and count definitions](../../../../metal-microbench/metal_recording.m#L431) · [Synchronization request](../../design/synchronization-signature-change-request.md)
- **Transport.** In that evaluator, `deliver` copies the selected bytes with `memmove` and publishes the receive word. This exercises numerical and page-offset agreement. The earlier two-host fan-out run observed the bridge itself send 131,072 bytes before the change and 65,536 after it across two invocations. A separate two-host run observed the consumer compute the first 4,096 correct results while the producer withheld the second half. Those observations discriminate duplicate traffic and a whole-tensor wait, respectively. [Local delivery](../../../../compiler-emit/artifacts/joint-sharding-20261119/evaluate.py#L132) · [Two-host measurements](../../design/cross-call-publication-and-fanout-2026-11-18.md)
- **Gradients.** The callgraph evaluation differentiates a placed Python FX graph and compiles a separate forward graph. A different existing client already exports the joint graph for `(x.sin() * x).sum()`, checks both loss and gradient against eager autograd, and runs that same graph through the CPU package and Metal recorder. Both targets again matched loss and gradient on two inputs on 19 November. That joint graph has compiled-backward coverage. [Placement evaluation](../callgraph-20261118/run.py#L38) · [Joint client](../../../../compiler-emit/artifacts/frontend-20261118/evaluate.py#L87) · [CPU and Metal results](../../../../compiler-emit/artifacts/frontend-20261118/review.md)

For a review, ask which reported result would change if the assigned producer stopped supplying its value. Often the direct consumer answers that question in a few lines of source. When performance is the claim, the existing executions already provide observables such as physical bytes, dispatches and progress on a partially arrived operand. A bibliography, a plan label and a correct final tensor can all survive the loss of the very transformation under review.
