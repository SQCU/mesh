# Directed routing and reuse of receive pages, 19 November 2026

## A: Where the extra constraints came from

Each cable endpoint advertised a rate. The bridge took the lesser rate and reported it in both directions. The compiler repeated that minimum, required symmetric routing operands and called its packer separately on each function's demands. R5 subsequently ordered the resulting hops across calls. It could change when the bridge sent those bytes, but the earlier packing calls had already chosen their paths. A3 assigns a rate to each direction, A4 assigns the complete transfer set to routing, and R5 prices each directed resource. [A3 and A4](../../design/aot-compilation-change-request.md#a3-costs-supply-task-and-transfer-weights) · [R5 and R6](../../design/plan-to-bridge-change-request.md#r5-one-solve-orders-computation-and-transfers)

On the extent transport, a second receive could overwrite storage still in use by a numerical reader. The installer handled this real dependency by waiting for a credit the host published after the entire Metal invocation returned. It applied the same delay to disjoint ranges. D.3.5 identifies the narrower dependency directly. Each receive needs its preceding receive and the completed uses of the bytes it will overwrite. ## B: What the compiler gives the consumers

The topology producer sums cable rates separately in each direction. One topology table supplies the endpoints, directed capacities and rate operands for every body in the block. The compiler passes all demands to the same Garg–Könemann packing call. A repeated body contributes its bytes times its occurrence count. Each body receives its own integral byte ranges from the solution. The bridge can select cables using the rate for the direction of that transfer. Each rank still refers to its adjacent peer in the compiled program. [Compiler and projection](../../rdma/mesh-collective.c) · [Flow solver](../../rdma/mesh-graph.c) · [Bridge's directional cable choice](../../../mesh-byte-extents-20261024/rdma/mesh-peer-plan.h)

In a fresh FX compilation, rank 0 could reach rank 1 directly at 80 Gbit/s and rank 1 could return at 40 Gbit/s. A second forward path ran through rank 2. Both default topology input and explicit directional weights gave the same split of a 65,536-byte demand, 35,317 direct and 30,219 through the relay. Adding two calls that sent their own results from rank 2 to rank 1 shifted all 65,536 bytes of the first demand to the direct path. Each reopened program exposed the selected routes and a single shared topology. A separate compilation supplied 100/20/40-Gbit/s arcs. The scheduler priced the same-sized hop at 1, 5 and 2.5 respectively in its normalized units. These are compiler results on supplied topologies.

The existing repeated-call client freshly compiled both direct and relayed routes. Source admission, peer posting order, numerical results and the caller's updated weight passed. The CPU check used Torch's C++ compiler with precompiled headers disabled because the local header cache contained a stale modification time. [Existing input program](../../../../compiler-emit/artifacts/joint-sharding-20261119/evaluate.py)

The extent registration and Metal program use actual reader completion for a reused landing range. On one Mac, a fresh two-rank program sent two 16-KiB ranges. Two operations consumed the first range and a third needed the withheld second range. After the first range's readers completed, the client wrote the next execution's changed bytes into that same range while the first execution was still active. The second range remained ineligible. Fresh and reopened Metal runs both returned the three eager tensors on each invocation. This exercised GPU execution and the registered-layout predicates using local delivery.
