The program needs the longest bound to choose its unroll horizon. That maximum alone cannot identify the next safe write to a particular tensor. The host-write lead and the number of storage copies describe different things. ## B: What each producer owes its consumer

The buffer solver associates each reuse bound with the value or extent that prompted the query. The allocator consumes those answers and the selected schedule's completion order. It computes how many copies each value needs across the common unroll horizon. The tensor's writer, numerical readers and any transport that still touches its bytes determine when the allocator can reuse a frame. Caller-visible values also keep their stated lifetime. [Modulo variable expansion, C3.3](../../design/disjoint-pages-change-request.md#c33-modulo-variable-expansion-produces-copies) · [Allocation, A5](../../design/aot-compilation-change-request.md#a5-allocation-produces-page-bindings)

The FX placement stage takes the exported graph, processor and topology operands, supplied costs and any explicit sharding constraints. It uses the operator's sharding rules to produce legal layouts. Joint selection scores those layouts with their actual transfer demands. Matching shards feed the reader locally. For different layouts the existing reshard transformation moves the required tensor sections. The same final lowerer consumes either selection. An observable comparison holds the graph, topology, constraints and inputs fixed, changes only the weights, and checks the collective payloads and returned tensors.
