# Source submission and rank work, 19 November

## A: The physical call index chose the bound and the bridge chose the work site

Before this revision, a partitioned matrix call supplied one function family per extracted body. A limit of one on two matrix invocations advanced each shard to itself in the next block. The source graph had required completion of the first matrix call before submission of the second in the same block. The bridge planner also assigned the first network rank to every function with zero transfers. Its work duration came entirely from transfer weights. A numerical function on the second rank could therefore cost zero on the first. ## B: One source relation connects work to submission

For each original function family, index a call by its position `i` in the family's row of `n` source calls. With a limit `b`, division of `i + b` by `n` gives the number of block iterations to advance. Its remainder selects the next submission in the row. The graph header computes this relation once. From the source-to-physical correspondence it projects the completing pieces of each invocation onto the submitting pieces of its successor. A source call with no executable work still occupies its place in the original row. When such a call names the target, the next nonempty source submission in the same family carries the condition. [A10](../../design/aot-compilation-change-request.md#a10-call-analysis-produces-ordering-and-concurrency-bounds) · [Graph functions](../../rdma/mesh-graph.c)

The buffer-capacity graph, target emitters and native IPC graph take that same relation. On each participating rank, a bound connects a work completion to a host submission with its block distance. The existing host FIFO can witness completion at the earliest of these later submissions. Shared preparation and public result assembly receive their ordinary data dependencies. The already compiled block window bounds their occupancy when they have no source-family completion to witness. The bridge uses the IPC graph to compute the existing BSL queue bounds. Placement supplies the numerical rank for each executable FX operation. Transport supplies the source, destination and relay ranks of the chosen link instructions. For each rank the scheduler computes the longest path through the selected dependencies and within-block resource orders, charging each instruction its supplied duration on the ranks it uses. The original function schedule retains that rank's duration. The IPC graph reads it for every occurrence. ## Observations

On one Mac, a two-rank topology placed `return x.sin(), x.cos()` on rank 1 with zero transfers. We supplied durations 3 and 7. A single resource produced a work vertex on rank 1 with duration 10. Two independent resources produced duration 7 on the same rank. Saving and reloading each native compilation returned the same rank-duration vectors, respectively `[0,10]` and `[0,7]`, and the same completion-to-submission edge `(0,0,2)`. The bridge graph and analysis read the same source-successor array in memory in both the fresh and loaded cases. These values are compiler costs in the units of the supplied weights.

For original families `A,B,A` with limits 1 and 3, physical memberships `[0,1]`, `[2]`, `[4,5]` produced four A-to-A pairs within the block, four across the boundary, and `(2,2,3)` for B. Physical piece 3 stayed independent of those source limits. The existing sharding client executed both layout splits and all six direct/relay fusion comparisons against eager Torch. Its local page copies supplied transport. The existing Metal client ran all four call graphs after saving and reopening the new format. A separate invocation opened the prior 143,248-byte program and preserved returned aliases and independent mutable state through four calls.

## A: Storage used a source bound to order work on different ranks

The capacity calculation used a single entry and exit for every physical call. For two bounded calls with an independent operation on each of ranks 0 and 1, it placed all four first-to-second operation pairs in dependency order. Its native IPC counterpart orders two pairs, one for each rank. A false path through the capacity graph can make two buffers appear to have disjoint lifetimes.

## B: Storage and completion-time scheduling read the same rank ports

Each selected schedule records the ranks touched by each instruction. Placement supplies the numerical rank, a transfer event names its rank, and each routed hop names both ends of its directed link. An external formal or return has no execution site. Format 6 saves the rank masks next to the instruction weights. The rank ports connect the completion on each participating rank to that rank’s host submission. The per-rank submission order continues through calls with no local work. A commuting-chain edge orders only work on ranks the two calls share. The completion-time solver takes the zero-distance edges for its single block. Storage takes the same ports and all block distances. [Instruction placement](../../rdma/mesh-collective.c) · [Rank admission](../../rdma/mesh_graph.py) · [IG-5](../../design/compilation-coordination.md)

In the capacity graph for two independent ranks at limit one, the two same-rank work pairs were reachable in the current block. Neither cross-rank pair was reachable. The reverse same-rank pair was reachable one block later. At limit two, the second same-rank call could issue in the current block. In a rank-0, rank-1, rank-0 sequence, the first and third calls on rank 0 remained ordered and the middle rank-1 call remained independent. The saved and reopened numerical example retained masks `[0, 2, 2, 0]` for its formal, two rank-1 operations, and return.

Before the compiler selects transfer cuts, the source analysis uses the outer FX call edges for cross-call data and effect dependencies. After selection, storage uses the instruction endpoints of the whole-program access and effect relation. Source admission uses rank ports in both graphs. Source analysis has no relay instructions until routing selects the path. Older saved formats omit per-instruction rank masks and can still execute the programs they contain.

## A: Local resource numbers serialized independent devices

Two ranks could both receive resource number zero for a numerical operation. The body scheduler assigned the same processor to these operations. It also assigned zero-duration event records to the first directed link. Both choices introduced resource-order edges between instructions that use different hardware. The capacity calculation then repeated each body's local resource order for every occurrence.

## B: The selected processor or directed link supplies the resource order

The body producer names a numerical resource by rank, backend and the weighting function's resource number. Each routed instruction names its directed link. A formal, return or zero-duration event has no resource cycle. The capacity calculation reads the selected program's resource cycles across all call occurrences, including the return edge to the next block. R5 uses the same resource identities to price contention. We compiled `return a.sin(), b.cos()` with independent inputs, on ranks zero and one, and supplied weight four and resource number zero for both operations. The two numerical vertices used separate resources in the body and in the program. Direct searches of the selected capacity graph reached neither operation from the other within a block. Both operations belonged to a resource cycle that advanced one block.
