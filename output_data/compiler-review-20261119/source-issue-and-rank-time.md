# Source submission and rank work, 19 November

## A: The physical call index chose the bound and the bridge chose the work site

Before this revision, a partitioned matrix call supplied one function family per extracted body. A limit of one on two matrix invocations advanced each shard to itself in the next block. The source graph had required completion of the first matrix call before submission of the second in the same block. The bridge planner also assigned the first network rank to every function with zero transfers. Its work duration came entirely from transfer weights. A numerical function on the second rank could therefore cost zero on the first. ## B: One source relation connects work to submission

For each original function family, index a call by its position `i` in the family's row of `n` source calls. With a limit `b`, division of `i + b` by `n` gives the number of block iterations to advance. Its remainder selects the next submission in the row. The graph header computes this relation once. From the source-to-physical correspondence it projects the completing pieces of each invocation onto the submitting pieces of its successor. A source call with no executable work still occupies its place in the original row. When such a call names the target, the next nonempty source submission in the same family carries the condition. [A10](../../design/aot-compilation-change-request.md#a10-call-analysis-produces-ordering-and-concurrency-bounds) · [Graph functions](../../rdma/mesh-graph.c)

The buffer-capacity graph, target emitters and native IPC graph take that same relation. On each participating rank, a bound connects a work completion to a host submission with its block distance. The existing host FIFO can witness completion at the earliest of these later submissions. Shared preparation and public result assembly receive their ordinary data dependencies. The already compiled block window bounds their occupancy when they have no source-family completion to witness. The bridge uses the IPC graph to compute the existing BSL queue bounds. [Planner](../../rdma/mesh-collective.c) · [BSL and submission semantics](../../design/algorithm-sources.md#the-plans-results-for-native-preparation) · [Storage capacity](../../rdma/mesh_graph.py)

Placement supplies the numerical rank for each executable FX operation. Transport supplies the source, destination and relay ranks of the chosen link instructions. For each rank the scheduler computes the longest path through the selected dependencies and within-block resource orders, charging each instruction its supplied duration on the ranks it uses. The original function schedule retains that rank's duration. The IPC graph reads it for every occurrence. ## Observations

On one Mac, a two-rank topology placed `return x.sin(), x.cos()` on rank 1 with zero transfers. We supplied durations 3 and 7. A single resource produced a work vertex on rank 1 with duration 10. Two independent resources produced duration 7 on the same rank. Saving and reloading each native compilation returned the same rank-duration vectors, respectively `[0,10]` and `[0,7]`, and the same completion-to-submission edge `(0,0,2)`. The bridge graph and analysis read the same source-successor array in memory in both the fresh and loaded cases. These values are compiler costs in the units of the supplied weights.

For original families `A,B,A` with limits 1 and 3, physical memberships `[0,1]`, `[2]`, `[4,5]` produced four A-to-A pairs within the block, four across the boundary, and `(2,2,3)` for B. Physical piece 3 stayed independent of those source limits. The existing sharding client executed both layout splits and all six direct/relay fusion comparisons against eager Torch. Its local page copies supplied transport. The existing Metal client ran all four call graphs after saving and reopening the new format. A separate invocation opened the prior 143,248-byte program and preserved returned aliases and independent mutable state through four calls.
