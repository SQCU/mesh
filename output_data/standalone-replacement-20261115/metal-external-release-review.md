Mesh’s required architecture represents allocation, lifetimes, placement, dependencies, and schedules as explicit data because these are solved ahead of execution and must remain available to later transformations.
Producers publish complete results in paged storage, and consumers access those same results by view, preserving their identity and page-table references.
Compilation therefore composes functions of explicit operands and represented effects, with original objects or argument bundles passed through existing interfaces using `*args` and `**args` where appropriate.
This is a stronger functional discipline than ordinary Python programming: every agent must recognize copying or reconstructing existing results as a departure from the specification and correct its work.

Every descendant function accesses produced structures through views of the same storage, with their page-table references carried intact.
Passing a view preserves access to the complete structure while each consumer dereferences exactly what its algorithm uses.
Packing, unpacking, or selecting fields into smaller replacement structs along that chain is unnecessary because the complete structure is never passed by copy.
Throughout this integration, agents use access by view to avoid spending memory bandwidth and stack work on duplicated representations, especially across Apple Silicon’s bandwidth-limited interconnect.

# Independent review: MetalExternalHold / MetalExternalRelease

2026-11-15. Codex source/API review, requested without presuming a defect. Reviewed Metal `1703f8df960d0ef415b9c8d3dde075e136c5f650` and Mesh `2f78b2efdfd81d2443b0b6b3e018b06ead1873ee`. Deliberate callback-error markers are disregarded when analyzing the original bodies. No implementation changes, imports, builds, or workloads were performed. Line anchors below refer to these snapshots; marker restoration may shift them.

**Finding:** the release callback, reference counting, and synchronization have legitimate lifetime duties in the existing asynchronous interface. No intrinsic retain-count or race defect in `MetalExternalRelease` was established. Its extra array copy and overly broad residency membership are avoidable work. A separate, concrete caller teardown gap discards the native “not drained” result.

## Actual ownership and completion chain

1. [MetalExternalScan](/Users/mdot/metal-microbench/metal_program.m:1518) produces each external root's argument identity, CPU/GPU use and actual binding sites once. Fixed, already placed roots are excluded. `MetalExternalRecord` saves these records; `MetalExternalRead` borrows their bytes from the archive retained by `MetalProgramMake`. [MetalExternalResidency](/Users/mdot/metal-microbench/metal_program.m:1599) creates one shared residency set if any external root has a GPU use, attaches it to the queue, and creates the counted membership owner.
2. [MetalProgramExecute](/Users/mdot/metal-microbench/metal_program.m:2064) constructs a fresh, private `NSMutableArray`, appending every non-null argument buffer. The list is not subsequently mutated and has no caller-supplied mutable alias. `Hold` adds residency on the first outstanding reference and counts every occurrence. Submission may return while GPU work remains outstanding. `Release` registers one notification for the batch's last issued event value, carrying the same list membership.
3. [MetalExternalRelease](/Users/mdot/metal-microbench/metal_program.m:2032) makes a **shallow object-list copy**, not a tensor-data copy. The escaping block captures that array, the counted set, residency set and dispatch group. Copied blocks retain captured Objective-C objects; the explicit array release balances the original `copy`, while block destruction releases its capture. The local variable aliases do not themselves create dangling referents. [Apple Blocks ownership](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Blocks/Articles/bxVariables.html) and the installed SDK's `usr/include/os/object.h:39` also establish GCD-object retention under the build's default Objective-C dispatch-object mode.
4. [MetalProgramMake](/Users/mdot/metal-microbench/metal_program.m:1748) owns the recorder, serial listener and notification group; [MetalCompletionKeep](/Users/mdot/metal-microbench/metal_program.m:380) retains completion events. `MetalProgramProject` emits submission followed by the final queue/host event signal. The installed SDK's `MTL4CommandQueue.h:261` defines queue signalling after preceding GPU work completes; `MTLEvent.h:54` schedules notification on the listener queue once the value reaches its target. Therefore registration after submission remains meaningful even if the event has already advanced.
5. [MetalProgramEnd](/Users/mdot/metal-microbench/metal_program.m:1976) waits for the execution event, then drains the notification group. Release decrements counts, removes only final references, commits residency changes, releases the held list, then leaves that group. GPU completion alone is not host-notification drain. `ETIMEDOUT` expressly leaves work/operands live; cancellation reported after successful drain is different. [Program deallocation](/Users/mdot/metal-microbench/metal_program.m:349) removes queue residency sets and releases listener, events and other owners; it does not itself perform this drain.

## Which mechanisms are justified?

| Mechanism | Judgment and actual reason |
|---|---|
| Strong resource ownership through completion | Required boundary work. Metal 4 command buffers do not strongly retain their resources. An invocation must retain the actual storage owners through their uses; a raw buffer/base address is insufficient as an ownership interface. [Metal 4 resource lifetime](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api) |
| Aggregate membership counts | Legitimate for this shared-set interface. The same buffer can occur in several argument slots or outstanding batches. Balanced increments/decrements prevent the first completed batch from removing another batch's residency. This is exactly the multiplicity represented by [NSCountedSet](https://developer.apple.com/documentation/foundation/nscountedset). Metal itself does not require this particular container. |
| `@synchronized(counts)` | Justified here: Hold runs on the caller's thread and Release on the listener's queue. Serializing callbacks alone does not serialize Hold against Release. Both count transitions and residency mutation/commit must be coordinated; `@synchronized` is one mechanism, not a mandated API. |
| Residency add/remove and `commit` | Legitimate API work for changing dynamic bindings. Residency-set methods are not thread-safe, staged changes need `commit`, and removal must respect remaining GPU uses. Residency does not track hazards or replace the schedule's synchronization. [Residency-set contract](https://developer.apple.com/documentation/metal/mtlresidencyset) |
| Second array copy | Avoidable with the observed producer. Retaining membership is necessary, but isolation from concurrent list mutation is not: Execute owns the only mutable list and finishes filling it before Hold/Release. A retained view of one immutable invocation binding owner can supply that membership without another list copy. This finding does not imply that the original `copy` is unsafe. |
| Every non-null buffer becoming resident | Confirmed unnecessary generalization. Once any external GPU use creates the set, Execute includes even a non-null buffer belonging to a CPU-only argument. Prepared `MetalExternalUse` already retains the actual distinction. Consume that result when forming the owned binding view; no runtime rediscovery is needed. No correctness failure or measured cost is claimed. |

The counts support **overlapping asynchronous submissions**, not a proven license for simultaneous host calls on one `MetalProgram`. Execute mutates program counters, progress state and completion history outside this lock. The normal [Bound.invoked](/Users/mdot/dox/mesh/compiler/mesh_compiler/native.py:1495) path calls End after each invocation. Neither this source trace nor Metal's thread-safe queue submission establishes whole-Program host-thread safety.

## Confirmed caller gap; limits of the finding

[Owned.released](/Users/mdot/dox/mesh/compiler/mesh_compiler/native.py:69) calls each cleanup and ignores its return. [Target.prepare](/Users/mdot/dox/mesh/compiler/mesh_compiler/native.py:1266) registers `MetalProgramEnd` in that cleanup chain, followed in reverse cleanup order by releases of the event, program and earlier owners. Thus the original bodies proceed with teardown even when End returns `ETIMEDOUT` and explicitly says operands remain live. This is a confirmed loss of the completion contract at the caller, **not proof of an observed use-after-free inside Release**. Other retained references may delay individual destruction; they do not turn the discarded drain result into an ownership guarantee.

Bound.invoked also unwinds its local owner pool and releases its borrowed-buffer references in `finally` on an End error. Do not conclude that this alone frees every GPU backing: [MetalBufferBorrow](/Users/mdot/metal-microbench/metal_capture.m:1553), reached through [paged](/Users/mdot/dox/mesh/compiler/mesh_compiler/native.py:1478) and [metal._placed_buffer](/Users/mdot/dox/mesh/compiler/mesh_compiler/metal.py:151), retains a CPU storage owner through the buffer's deallocator; Release retains those buffers. Installed Torch `ATen/mps/MPSAllocator.h:280` also explicitly accounts for buffers with extra retain counts. The remaining host bases, tensor handles and program-owned resources still need their actual owners; this review did not establish a runtime failure for each storage kind.

There is already a positive drain consumer: [e2b_replay's End result](/Users/mdot/metal-microbench/tools/e2b_replay.m:1693) preserves `running` on timeout, and its [retired path](/Users/mdot/metal-microbench/tools/e2b_replay.m:1777) returns without destroying live transport/program operands. This is source evidence, not a workload observation.

No premature release was established for the normal, successfully drained path. No callback latency, lock contention, allocator-reuse failure, or speedup was measured. No allegation follows merely from notification delivery, shallow copying, or locking.

## Replacement boundary for the independent modules

`compiler-emit` should retain the complete prepared binding/use/lifetime result; `native-execution` should consume it by view together with the actual invocation storage owner. That owner must cover the original tensor/storage handles, dynamic buffer membership and completion interval, while fixed resources remain with their prepared owner. The existing per-root use/site result supplies GPU membership; do not rebuild a second all-argument resource list.

The execution completion result must distinguish **drained** from **still live**, including error exits. Teardown consumes that result before releasing the program, listener, event, bindings or storage owners. Preserve aggregate last-use behavior when invocations overlap; do not remove synchronization solely because the list copy is avoidable. This defines the required owner/result handoff without prescribing a new registry, dispatcher, callback replacement, or per-call allocation scheme. Original Metal notification APIs can remain legitimate boundary operations.

Source review and official API documentation establish the reasoning above; they are not build or execution validation.
